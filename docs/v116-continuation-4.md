# Продолжение 4 — страничный тепловой граф и стабильные слоты

## Статус

Реализовано локальное обновление тепловых связей. Версия остаётся **1.16.0-rc.7**: тепловой критерий ≤2 мс и остальные открытые условия общей приёмки не объявляются закрытыми.

Окончательные exit-коды и измерения добавляются ниже после завершения последовательных проверок. Промежуточный кандидат не подменяет итоговый код.

## Хранение и физика

Новый `src/sim/heat-cache.ts` хранит узлы в числовых ID-страницах по 16 записей и использует отдельные стабильные слоты для температур, энергий и потоков. Большой ID не определяет размер typed-array: слот зависит от числа реальных узлов. Освободившиеся слоты переиспользуются.

При правке копируются каталоги страниц и только затронутые страницы/записи соседей. Неизменённые страницы и канонические пары разделяются между снимками; цепочки родителей кэша нет. Обёртка HeatNet меняется, старые снимки соседей сохраняются. Это не строгий O(delta): каталоги страниц копируются, расширение scratch-буфера амортизированно может потребовать полного заполнения теплоёмкостей. Пул слотов/буферов сохраняет прежний максимум нагрузки.

Рёбра принадлежат меньшему ID и внутри строки упорядочены по большему ID. Типизированные строки слотов упаковываются только для затронутых страниц. Обычная правка не переиндексирует все оставшиеся рёбра. HX-компоненты переиспользуются только вне затронутых HX-связей; при изменении HX-связей остаётся консервативный BFS. Полный fallback для heatDirty=true, загрузки, отсутствующего кэша и изменений модов сохранён.

Сам перенос тепла проходит по упорядоченным страницам **внутри stepHeat и измеряемого Game.step**: температуры старой фазы, целые джоули, четыре прохода ограничений потоков и применение в прежнем порядке. Уравнения, округление, реакторные команды, пар, потери, аварии и заражение не менялись.

`ents`, `edges`, `caps`, `edgeA/B` сохраняют каноническое представление для инспекции, подсказок и старых потребителей. Плоские снимки собираются лениво из уже готовых строк. Чтение edges.length получает реально поддерживаемое число рёбер без копирования массива всех пар. Это не перенос построения графа за timed step: обнаружение портов, создание изменённых пар, их порядок, индексы стабильных слотов и типизированные страницы выполняются при настоящей перестройке в heat-фазе. Подсказки могут читать канонический снимок, но перенос тепла не использует этот снимок.

## RED и проверки

`tests/heat-delta-storage.test.ts` сначала упал на прежнем коде: запрет чтения полных cached.ents/edges и обхода всех соседей обнаружил полный проход. Новый тест проверяет одну правку в сетке, ограниченное число изменённых записей/строк, отсутствие глобальной переиндексации, идентичность незатронутых пар и сохранность предыдущего снимка.

Проверены 40 remove/build/save/replay-циклов со стабильным переиспользованием слотов. При каждом replay совпадают физические hash и ядерные счётчики. Отдельная проверка классификации помнит прежний тип записи, а не перечитывает изменённую Entity-ссылку.

Исходные heat-local-rebuild, heat-component-index и heat-explosion-batch проходят, включая редкий ID 2 млрд, все повороты, модификацию теплоёмкостей и полный fallback. Аварийный тест сохраняет прежний hash `999283ce28e16b6e` и исправленный учёт потерь. Старые тесты не редактировались.

## Независимое сравнение с прежним исходником

Заморожено полное дерево source предыдущего продолжения: `integration-logs/continuation-4/baseline-src`. Независимый скрипт `docs/.heat-delta-parity.once.ts` загружает обе реализации из одного снимка, а не переключает режим нового алгоритма.

Все 600 шагов совпали по stateHash, полному сохраняемому состоянию, ядерным счётчикам и зонам. Сценарий включает HX-связанный split/merge, редкие ID, поворот, подтверждённую аварийную остановку настоящей командой, save/load в середине, модификацию теплоёмкости с full-dirty, удаление/восстановление HX и настоящий взрыв.

Первая диагностическая попытка сравнения тоже совпала, но передала stop без on:true: реальная остановка не была включена. Эта попытка сохранена под physics-parity-no-stop и **не является доказательством остановки**. Исправленный диагностический сценарий явно подтверждает rstop и rt=0 после команды. Это исправление проверочного сценария, не игрового кода.

## Производительность и ограничения

Неизменённый обязательный стенд сохраняет 100 реакторов, 12 300 горячих теплопроводов, 1000 HX, 2000 турбин, 200 настоящих насосов и 100 реальных активных радаров. Все прогревы, число шагов, механика split/merge и nearest-rank p95 сохранены.

Первый страничный кандидат функционально прошёл, но замедлил обычные тепловые фазы и не прошёл их бюджет. Во втором убраны вложенные edge-итераторы горячего цикла: используются типизированные страницы и индексные циклы. Третий избегает плоского снимка всех пар при запросе только количества. Все отрицательные измерения сохранены, ни один порог не ослаблен.

После общего npm test отдельно измеряются свежий прежний source и окончательный кандидат, без параллельного тяжёлого процесса. Копия исходного стенда для прежнего дерева меняет только пути импортов; остальные строки побайтно совпадают после обратной подстановки импортов. Оригинальный стенд не изменён, его SHA256 проверяется.

Данные виртуального CPU не заменяют исходный Windows ПК, GPU или всю браузерную матрицу. Массовая авария остаётся отдельным одиночным пиком; p95 её обычных шагов не закрывает этот пик.
