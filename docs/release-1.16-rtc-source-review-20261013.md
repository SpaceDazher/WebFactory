# WebKit RTC: предел доказательства

Текущие E20/E27/E29 сохраняют полный счётчик ошибок. В E29 первая ошибка зарегистрирована на живом соединении cid3: DC open, PC/ICE connected, bufferedAmount195, выбранная srflx-пара succeeded. Остальные две возникают при teardown. Это не доказывает, что причиной первой ошибки был закрытый ручной peer. Одного дополнительного closing-guard недостаточно для доказанного исправления.

В первичном [исходнике WebKit RTCDataChannel.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/mediastream/RTCDataChannel.cpp) метод send ставит строку в NetworkSendQueue. Отказ sendStringData внутри очереди пишет сообщение об ошибке через ScriptExecutionContext; синхронный JavaScript try/catch не охватывает эту позднюю запись. close ждёт опустошения очереди перед закрытием её обработчика. Это объясняет механизм сообщения в текущем upstream, но не устанавливает причину сбоя именно установленного WebKit27.2.

Изменение в кандидате исправляет отдельный доказанный дефект жизненного цикла: закрытие идемпотентно, очищает DC и PC и сохраняет прежний callback при привязке Session. Chromium/Firefox HTTP E29 доказывают closed для старой карточки и peer, повторное соединение и совпадение состояния. WebKit остаётся красным; фильтры KNOWN, подавление native console/page errors, изменение порогов и непроверенный workaround не применяются.

Следующий ограниченный этап: привязать ошибку к конкретному enqueue/send и времени native readyState/error/close на обеих сторонах; отдельно воспроизвести живую отправку и закрытие после очереди. Исправление принимать исходными E20/E27/E29 на WebKit плюс Chromium/Firefox, без подмены RTC ретрансляцией только ради зелёного теста.
