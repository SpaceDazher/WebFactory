### v1.17 — Серверы, биотехнологии Роя, оборона и управление фабрикой

**Объём 1.17:** постоянный выделенный сервер, включая запуск сервера на своём ПК одной кнопкой и упрощённое приглашение друзей, производственная цепочка биоматериалов Роя, вторая биомеханика — клеточные пробы/геномная библиотека, выращивание зеркальных биороботов и управление отрядом, программируемый громкоговоритель, шесть видов оружия ближнего боя, специальный стационарный/личный дронопорт с шестью видами боевых дронов, настройка доступных ячеек всех сундуков, исправление отображения воды после насыпи, семь технологий расширения инвентаря с 32 до 256 ячеек, автоматическая укладка электростолбов с максимальным шагом провода и обозначение жидкостных входов/выходов НПЗ и химзаводов по выбранному рецепту. Новые игровые механики работают в одиночной игре, браузерном кооперативе и на выделенном сервере; они не входят в критерии выпуска 1.16. Подтверждённая исходная база — архив 1.15.0; зависимости от новых систем 1.16 являются требованиями к последующей интеграции.

#### 1. Выделенный сервер

**Цель.** Мир работает отдельно от окна игрока: владелец включает сервер на своём ПК из меню совместной игры одной кнопкой, друзья входят по короткому приглашению. Сервер доступен, пока ПК включён, не спит и серверный процесс работает; выход инженера и закрытие окна игры сами по себе его не останавливают. Для непрерывной доступности можно использовать VPS по прежнему сценарию выделенного сервера.

**Состав**

- `npm run server` — та же симуляция без интерфейса на Node (код Worker переиспользуется). Сервер — авторитетный участник lockstep, задающий шаг игры; приложение запуска использует тот же серверный модуль без ручного ввода команды.
- До 16 игроков. Основной вход для друзей — короткий код или ссылка; прямой адрес/пароль остаются в «Дополнительно». Сервер и клиент автоматически выбирают прямое WebRTC-соединение либо ретрансляцию через защищённый WebSocket, если прямой путь недоступен.
- **Сервер на своём ПК:** локальное приложение запуска входит в поставку для Windows, содержит нужный runtime, создаёт настройки/каталог мира, запускает сервер в фоне, показывает состояние и корректно останавливает его. В меню одна основная кнопка меняет действие «Включить сервер на моём ПК» ↔ «Выключить сервер».
- **Постоянный мир**: автосохранение каждые 10 мин, хранение последних 10 сохранений, пауза, когда никого нет (по настройке).
- **Администрирование**: файл настроек, консоль команд (`/kick`, `/ban`, `/save`, `/promote`), белый список, журнал событий.
- Образ Docker и инструкция по запуску на простом VPS.

**Готово, когда** сервер 24 часа держит мир с 16 ботами-игроками без расхождений и утечек памяти (рост ≤ 5%), а перезапуск сервера восстанавливает мир из сохранения.

**Как это выглядит для игрока**

- В «Совместная игра» видны две простые вкладки: **«Мой сервер»** и **«Войти к друзьям»**. Первая содержит выбранный мир и кнопку включения, вторая — одно поле приглашения и кнопку входа.
- Владелец нажимает «Включить сервер на моём ПК», после готовности копирует приглашение. Друг вставляет короткий код, ссылку или текст приглашения и нажимает «Войти»; служебный обмен соединения выполняется автоматически.
- Повторное нажатие «Выключить сервер» сохраняет мир и завершает процесс. Следующее включение продолжает тот же мир. Для владельца доступны «Играть» и статус фонового сервера; друзьям не требуется устанавливать серверный компонент.

**Файл настроек (пример)**

```json
{ "name": "Завод друзей", "maxPlayers": 16, "password": "...",
  "autosaveMinutes": 10, "pauseWhenEmpty": true, "admins": ["tema"] }
```

**Требования к серверу**

|Размер базы|Память|Процессор|
|---|---|---|
|до 5 000 построек|512 МБ|1 ядро|
|до 20 000 построек|1,5 ГБ|2 ядра|

**Порядок работ по серверному ядру (предварительная оценка):** неделя 1 — симуляция на Node без интерфейса; неделя 2 — соединения, вход/выход, сохранения; неделя 3 — админ-команды, Docker, нагрузочный тест. Поставка приложения, запуск одной кнопкой и публичная служба приглашений/relay оцениваются отдельными этапами после прототипа.

**Риски:** код Worker использует браузерные API. Мера — слой совместимости и тест «та же партия в браузере и на сервере даёт одинаковый результат».

**1.1. Поставка и честная граница одной кнопки**

- Подтверждённая база 1.15 — браузерная игра с `index.html`, модулями `src/net/rtc.ts`/`session.ts` и инструментом `tools/signal-server.mjs`. Уже поддерживаются короткие комнаты `ZVD-XXXX`, ручные длинные `Z7O/Z7J/Z7A` и ретрансляция при недоступном прямом соединении. Постоянного серверного процесса на ПК и локального приложения запуска в этой поставке нет; новые кнопки не должны обозначать работающую вкладку как независимый сервер.
- Для 1.17 поставить **приложение игры для ПК с серверным компонентом**: первоначально Windows, с включёнными совместимым runtime и файлами сервера. После обычной первой установки/запуска игры включение и выключение сервера выполняются из игрового меню по одной кнопке; отдельная установка Node, терминал и настройка роутера пользователю не нужны. Конкретный стек оболочки выбирается на прототипе, контракт управления и фоновая работа обязательны.
- В обычной браузерной версии та же карточка открывает установленное приложение через действие **«Открыть приложение для ПК»**. Если его ещё нет — понятный шаг **«Установить и открыть»** с официальной поставкой. Первое открытие/установка может требовать штатного действия ОС или браузера; нельзя обещать скрытую установку либо запуск произвольного фонового процесса из чистой веб-страницы. Это одноразовая граница платформы, после неё повседневный запуск автоматический. Chrome связывает нативные процессы с установленным host и ограниченным интерфейсом расширения; доступ к локальной сети также может требовать разрешения. Источники ограничений: [Chrome Native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Chrome Local Network Access](https://developer.chrome.com/blog/local-network-access). Native Messaging приведён как пример границы платформы, а не обязательный выбор расширения для игры.
- Управление осуществляется встроенным локальным мостом приложения. Из браузера переход открывает официальное приложение и нужный экран; права запуска остаются у него. Клиентское окно и серверный процесс имеют раздельный жизненный цикл. Установка происходит для текущего пользователя, сервер запускается без административных прав; стандартные запросы ОС не обходятся.
- Внутри процесса sim мир по-прежнему рассчитывается на ПК владельца. Служба приглашений/ретрансляции обеспечивает соединение, а не заменяет его ПК облачной симуляцией. При недоступной интернет-службе локальная игра/сервер могут работать, но вход из интернета не обещается. Поддержка macOS/Linux оценивается отдельно и не обозначается готовой до поставки и проверки.

**1.2. Простой экран владельца и гостя**

```text
СОВМЕСТНАЯ ИГРА
[ Мой сервер ]    [ Войти к друзьям ]

Мир: Северный завод                 Изменить
● Выключен
[ Включить сервер на моём ПК ]

После включения:
● Сервер работает                    Игроки: 0/8
Код:  ZVD-7K3M-P9XT
[ Копировать приглашение ]          [ Играть ]
[ Выключить сервер ]
Работает в фоне, пока ПК включён.
Дополнительно ▾
```

```text
ВОЙТИ К ДРУЗЬЯМ
Код или ссылка приглашения
[ ZVD-7K3M-P9XT                 ]   [ Вставить ]
[ Войти ]

Проверяем приглашение → Соединяем → Загружаем мир
```

- Владелец видит имя мира, текстовый статус с цветом/значком, число игроков и приглашение. Основной кнопкой остаётся включение/выключение; этап показан рядом, повтор одной операции блокируется. Во время подготовки та же кнопка предлагает «Отменить запуск», после принятой отмены или при остановке повторное действие недоступно до завершения. «Копировать приглашение» доступно, когда интернет-вход действительно готов. «Играть» подключает владельца как обычного участника с его правами; пребывание в мире не требуется для работы сервера.
- Мир по умолчанию — открытый сейчас, иначе последний выбранный совместимый локальный мир. Если сохранений нет, первый запуск создаёт мир с обычными стартовыми настройками. «Изменить» до запуска позволяет выбрать другой; запущенный сервер не меняет мир от выбора новой строки меню. В этой поставке одна кнопка управляет одним серверным миром на ПК, без создания нескольких процессов от двойного клика.
- Базовые настройки создаются автоматически: название по миру, **8 мест по умолчанию, предел 16**, автосохранение **10 минут / последние 10**, `pauseWhenEmpty=true`, вход по приглашению, владелец — администратор. «Дополнительно» содержит число мест, паузу без игроков, доступ/пароль/белый список, смену приглашения, запуск после входа в ОС и диагностику. Ручные адреса, порты и ICE-параметры не занимают основной экран.
- «Копировать приглашение» кладёт понятный текст с названием игры/мира, коротким кодом и ссылкой. Гостевое поле принимает любую из этих форм, извлекает приглашение и распознаёт его формат. Для короткого кода убирает пробелы/дефисы при проверке, приводит буквы к верхнему регистру и показывает единое форматирование; токен ссылки и служебная часть старого `Z7*` сохраняют исходный регистр/данные. Несколько разных приглашений в одном тексте требуют выбрать одно, а не входить в случайный мир. При отказе доступа к буферу работает обычная вставка; буфер не считывается без действия игрока.
- Перейдя по ссылке, гость получает заполненное поле и нажимает «Войти». Никакого ручного ответного кода в основном сценарии нет: ответы/подтверждения соединения идут внутри протокола. Совместимые старые форматы остаются в «Дополнительно» как запасной путь; совпадение кода не разрешает игру с несовместимой версией симуляции.
- Статус читается без цвета: «Выключен», «Подготовка сервера», «Запуск», «Проверка соединения», «Сервер работает», «Работает локально», «Сохраняем и выключаем» либо сообщение ошибки. Доступны управление клавиатурой, фокус поля, текстовое подтверждение копирования и объяснение причины недоступной кнопки. Процент прогресса показывается только для реально измеряемой загрузки; другие этапы используют короткий статус.

**1.3. Что делает включение автоматически**

1. Приложение проверяет комплект сервера/совместимость версии, каталог данных и отсутствие другого экземпляра. Для того же работающего сервера возвращает его статус вместо второго процесса; повреждённую или несовместимую поставку не запускает под видом готового сервера.
2. Выбирает мир, создаёт настройки и резервную копию перед переносом, получает исключительное владение этим `worldId`. Если открыт локальный мир, его симуляция останавливается на согласованном тике, сохраняется полный снимок с игроками/инвентарём/новыми состояниями 1.17 и проверяется возможность его чтения сервером.
3. Запускает тот же серверный модуль в фоне из включённого runtime, ожидает готовности симуляции и локального управления. Начальный снимок/контрольный хеш совпадают с переданным миром. После этого сервер становится единственным авторитетом; прежний локальный Worker не продолжает параллельно изменять ту же фабрику. Инженер из открытого мира переподключается к серверу с тем же стабильным id, без второго персонажа/инвентаря.
4. Регистрирует экземпляр в службе приглашений, связывает `serverId`, ключ владельца и срок приглашения. Проверяет доступность пути входа и автоматически выбирает прямую связь либо ретрансляцию. Код можно копировать только после успешной проверки доступности маршрута, а не сразу после создания строки.
5. Возвращает меню подтверждённое состояние, число игроков и приглашение. При старте из меню владелец может остаться в нём; при переносе открытой игры продолжает играть как клиент. Смена окна/закрытие игры оставляет фоновый сервер работающим и доступным через меню/значок приложения.

Если передача мира не удалась, локальная симуляция возобновляется только после гарантированного завершения неудачного серверного экземпляра; сохранённый снимок остаётся доступным. Если симуляция работает, но интернет-вход пока не готов, показывать **«Работает локально — подключение друзей из интернета недоступно»** и повторять проверку с ограничением частоты. Локальное состояние не маскируется зелёным «доступен друзьям», а исправление связи не создаёт второй мир/процесс.

**1.4. Приглашение и автоматический вход**

- Новый короткий код — предлагаемый формат **`ZVD-XXXX-XXXX`**: восемь случайных символов из алфавита без неоднозначных букв, сгруппированных по четыре; служба проверяет коллизии. Строка не содержит IP, порт, пароль администратора или имя файла. Длинные служебные `Z7*` остаются деталями совместимого расширенного режима. Конкретный алфавит/версия кодирования фиксируются вместе с протоколом; символы не заменяются эвристически так, чтобы получить другой действительный код.
- Код и ссылка — два представления **одного гостевого приглашения**, привязанного к миру/серверу/сроку и политике доступа. Ссылка несёт отдельный случайный токен не менее **128 бит**, сопоставленный тому же приглашению; ссылка и короткий код могут быть отозваны вместе. Начальный срок — **24 часа**, отображается владельцу. Обычный stop/start не продлевает срок и не меняет ещё действительный код; истёкший заменяется автоматически при следующей публикации готового сервера.
- Запись приглашения сохраняет владение при штатной остановке: до истечения гость видит «Сервер выключен — попроси владельца включить его». Этот код нельзя занять другим сервером после отключения. Владелец может сменить приглашение: старые код/ссылка больше не допускают новых гостей, уже подключённые игроки продолжают партию, пока не исключены отдельной командой. Выход/перезапуск и временная потеря сети не передают права на код чужому хосту.
- Для актуального присутствия сервер отправляет подтверждение работы каждые **10 с реального времени**; после **30 с** без подтверждения служба показывает «Сервер не отвечает», сохраняя привязку приглашения. Сон/обрыв не превращают старый статус в обещание доступности. Возврат подтверждённого владельца восстанавливает присутствие, не переиздаёт персонажей и не продлевает срок приглашения. Эти сетевые сроки не зависят от игровой паузы.
- «Войти» выполняет разрешение приглашения, проверку срока/версии/набора данных/мест/прав, установление транспорта, передачу мира и подтверждение готовности. Гость видит один линейный процесс без смены экранов с техническими настройками. После первого входа выданный ключ переподключения сохраняет привязку к персонажу; ротация приглашения не превращает его в нового инженера. Отзыв/бан игрока отдельно аннулирует его право входа.
- В простом режиме знание приглашения даёт гостевой доступ без дополнительного одобрения на каждое подключение. Пароль/белый список включаются владельцем в расширенных настройках и показывают один понятный дополнительный шаг, если нужны. Приглашение никогда не даёт локальное управление сервером, административную роль или доступ к произвольным файлам ПК; имя игрока не подтверждает права администратора.
- Служба ограничивает подбор/злоупотребления: стартово **не более 10 неуспешных разрешений в минуту с источника**, отдельные пределы для массовой регистрации/подключений и предельный размер сообщений. Секреты приглашения/владельца/переподключения не попадают в диагностические логи целиком. Показанная владельцу связь защищает регистрацию от переиспользования чужого `serverId`; короткий код не используется как ключ владельца.

**1.5. Соединение через интернет без ручной настройки**

- В поставку включить адреса официальной службы приглашений и ретрансляции с защищённым соединением. Приложение сервера само открывает исходящее соединение; гость подключается к той же службе. При возможности стороны выбирают прямой WebRTC-путь, при невозможности — защищённый relay. При смене маршрута сохраняются сессия/персонаж и порядок пакетов; дубли подтверждаются и отбрасываются по протоколу.
- Основной сценарий не требует ввода публичного IP, проброса портов, UPnP, изменения правил брандмауэра либо покупки выделенного адреса. Исходящее соединение и ретрансляция обязательны для проверки на домашнем NAT, CGNAT/мобильной сети и сети без UDP. Если сеть блокирует и доступ к службе, показывается понятная причина; одной кнопке не приписывается способность обходить любую блокировку.
- Работающая вкладка не должна оставаться скрытым обязательным ретранслятором/хостом. Если окно владельца закрыто, соединения гостей и симуляция обслуживаются серверным компонентом. Текущий `tools/signal-server.mjs` — база для оценки повторного использования; его наличие само по себе не доказывает эксплуатационную готовность публичной службы с новым доступом/сроками/состояниями.
- Для выпуска выбрать операторов/адреса службы, её лимиты и обслуживание, измерить трафик/задержку/стоимость relay на 16 участниках, обеспечить TLS и совместимый протокол. Это обязательная внешняя зависимость обещания «вход по коду из интернета», а не настройка, которую обычный игрок должен создавать сам. При отказе службы локальный сервер сохраняет мир; существующие прямые связи могут продолжаться, relay-связи показывают потерю связи и восстанавливаются без двойного входа.

**1.6. Выключение, фон и восстановление**

- Нажатие **«Выключить сервер»** запускает одну операцию без дополнительного подтверждения: закрывается вход новых игроков, участники получают сообщение об остановке, заканчивается текущий согласованный тик, выполняется финальное сохранение и проверяется его запись. Только после успешного сохранения закрываются соединения/процесс и освобождается владение миром; в меню остаются выбранный мир и кнопка включения. Старые резервные копии сохраняются.
- Если запись не удалась, сервер остаётся в состоянии остановки с сохранённым в памяти миром и текстом «Не удалось сохранить мир», доступно «Повторить сохранение». Он не сообщает успешное выключение и не уничтожает единственную актуальную копию. Принудительное завершение — отдельное расширенное действие с явно указанной потерей несохранённого прогресса; не является скрытым автоматическим шагом.
- Закрытие обычного игрового окна оставляет сервер в фоне, что заранее видно в карточке. Значок серверного приложения в трее показывает состояние и даёт ту же команду остановки. Завершение самого фонового приложения использует сохранение/остановку, а не молча оставляет потерянный процесс. Автозапуск после входа в ОС — отдельный выключенный по умолчанию параметр; меню и автозапуск используют один контроллер экземпляра.
- Сон/выключение ПК означают недоступность сервера; их нельзя изображать как продолжение партии в облаке. При доступном уведомлении ОС приложение пытается сохранить мир, но внезапная потеря питания ограничивает восстановление последним успешно записанным снимком. После сна проверяется связь/исключительное владение, логические сроки мира продолжаются от симуляции, без бесплатного ускоренного проигрывания часов отсутствия. `pauseWhenEmpty` применяется к симуляции, а не к доступности приглашения.
- После аварии приложение обнаруживает оставшийся статус, проверяет последний целый снимок и предлагает **«Восстановить сервер»** одним действием. Оно не запускает пустой мир поверх повреждённого сохранения и не перезапускается бесконечно. Двойной клик, повтор команды, повторный вход приложения и stop во время подготовки сходятся в один контроллер состояния; проверяются собственные pid/идентификатор экземпляра, посторонние процессы не завершаются.

**1.7. Контракт управления и хранения**

- Предлагаемые операции контроллера: `status`, `start`, `stop`, `rotateInvite`, `openWorld` и чтение ограниченной диагностики. Команда содержит `requestId`, идентификатор разрешённого мира и ожидаемую ревизию состояния; повтор того же `requestId` возвращает результат операции. Состояния: `off → preparing → starting → online/local-only → stopping → off`, а также `error/recovery`. Повторный start возвращает уже работающий экземпляр, конфликтующая смена мира требует его штатной остановки.
- Локальный мост принимает только разрешённые действия доверенного приложения и проверяет права текущего пользователя/владельца, размеры и значения. Нет команд выполнения shell, произвольных путей или открытия управляющего интерфейса в интернет. Если реализации нужен loopback-интерфейс, его ограничить loopback, аутентификацией сессионным локальным секретом и проверкой разрешённого origin; случайная веб-страница/удалённый игрок не управляют ПК. Удалённые админ-команды проверяются сервером отдельно.
- Сохранять настройки запуска, выбранный `worldId`, `serverId`, привязку владельца, сведения о действующем приглашении/его сроке, настройки фона и последний подтверждённый снимок. Приватные ключи/локальные секреты хранятся в защищённом хранилище текущего пользователя, не в URL/приглашении/общедоступном файле. Запись мира выполняется через временный файл и атомарную замену с сохранением предыдущего целого снимка.
- Это данные приложения запуска и службы, с отдельно версионированной схемой; запланированный формат мира **19** остаётся тем же. Перенос включает все серверные состояния глав 2–5, пользовательские роли и sticky-флаг использования creative. Выключение не сбрасывает исследования, таймеры/биопроизводство, приказы, сигнализацию, заряд/фазы удара или права. Старые локальные миры не становятся опубликованными автоматически после обновления.

**1.8. Приёмка запуска сервера одной кнопкой**

1. На чистом поддерживаемом Windows-ПК после обычной поставки игры кнопка запуска работает без отдельно установленного Node, терминала, адреса/портов и ручной настройки роутера. В браузерном входе честно проверены первая установка/открытие приложения и штатные ограничения; гости входят из поддерживаемого браузера без установки серверного компонента.
2. Первое включение, двойной клик, повтор `requestId`, другой выбранный мир, отмена в подготовке и перезапуск меню создают ровно один серверный процесс и одного авторитета мира. Перенос открытой фабрики сохраняет хеш, персонажей, инвентарь и все новые состояния 1.17; неудачный перенос безопасно возвращает исходный мир.
3. Владелец включает/выключает готовый сервер одним нажатием. Закрытие игрового окна оставляет гостей в партии; выход фонового приложения корректно сохраняет мир. Следующее включение продолжает его, приглашение сохраняется до исходного срока; автозапуск выключен по умолчанию и не дублирует ручной запуск.
4. Гость входит по одному короткому коду, ссылке и скопированному тексту; ввод/вставка/форматирование/статусы понятны. Проверены неверный/истёкший/отозванный код, выключенный/полный сервер, несовместимая версия, нужный пароль, несколько кодов в тексте, запрет буфера и управление клавиатурой. Основной процесс не требует ручного ответного кода.
5. Вход и восстановление подтверждены на прямом соединении, домашнем NAT, CGNAT/мобильной сети, сети без UDP и принудительном relay; смена пути/потеря службы не дублируют персонажа/пакеты/ресурсы. Код не становится доступным для копирования до реальной готовности входа. Полностью заблокированная сеть показывает ошибку, локальный сервер остаётся доступным.
6. Штатная остановка, занятый/переполненный диск, ошибка финальной записи, сон/возобновление и аварийное завершение проверены на сохранениях. Успешное выключение означает целый финальный снимок; при ошибке нет ложного успеха, при аварии восстановление использует последний целый снимок без сброса мира/прав.
7. Приглашение даёт гостевые права, удалённый игрок/чужой origin не могут вызвать локальный start/stop, смену мира или произвольный процесс/файл. Проверены владение кодом после остановки, ротация/истечение, лимиты попыток, редактирование имени игрока и отсутствие секретов в логах; новый invite не обходит бан.
8. Проведены прежний 24-часовой прогон сервера с 16 участниками и отдельный прогон фонового приложения/службы на штатных stop/start и relay. Сравнены хеши и потеря/дубли данных, измерены время готовности, ресурсы ПК и трафик службы. Выполнена проверка понятности: **не менее 4 из 5 новых пользователей** запускают сервер и соединяются парой через приглашение без устного объяснения; целевой срок — **до 2 минут после установки**, без времени загрузки большого мира. Числа являются критериями будущей приёмки, а не результатом уже проведённого теста.

**Передача серверного интерфейса:** сначала фоновый контроллер и одна кнопка для локального мира → безопасный перенос/остановка → приглашение и автоматическое соединение → UI владельца/гостя и понятные ошибки → relay/ограничения доступа → фон/восстановление/нагрузка. Публичная служба и поставка приложения входят в объём реализации. Проверка одной кнопки без интернета не закрывает обещание простого входа друзей.

#### 2. Биоматериалы Роя: трупы, сбор слизи, извлечение и небольшие улучшения

**Согласованный замысел:** убитые существа оставляют трупы на 30–50 игровых минут; из разных видов собирается собственное сырьё. Сырьё вместе со специально собираемой слизью проходит технологическую переработку, открывает до четырёх небольших функциональных улучшений для каждого типа и превращается в материалы для боеприпасов либо специальных модулей брони. Ниже предложена рабочая модель реализации; количества, стоимость исследований и проценты являются стартовым балансом для прототипа, а не уже измеренными свойствами 1.15.

**Фактическая база:** `src/sim/enemies.ts` содержит ползунов `small/medium/big`, плевунов `spitter/spitter-big`, `armored`, `destroyer`, `flyer`, `brood`, `giant`, `queen`; черви `worm-small/medium/big/behemoth` представлены сооружениями Роя. `hitUnit` регистрирует гибель, а мёртвые юниты удаляются из активного массива; самостоятельного сохраняемого трупа Роя и биологической добычи нет. `Game.corpses` — тела инженеров с инвентарём и сроком 30 минут. Слизь уже хранится как интенсивность `creep` 0–255 на клетку, растёт у гнёзд и выжигается огнём/частично взрывом; добываемого предмета слизи нет. Новые останки не подменяют тела инженеров и не меняют выдачу их вещей.

**Логика процесса:** особенность животного объясняется материалом его тканей: панцирь — волокнами и минералами, сопротивление кислоте — защитным секретом, амортизация — вязкоупругими мембранами. Это основание для технологического материала, а не случайный «+5% за убийство». Промышленное разделение биомассы применяет фильтрацию и выделение фракций; исследования хитозановых материалов показывают возможность получать функциональные композиты из компонентов оболочек. Эти принципы используются как правдоподобная основа игрового процесса. Свойства инопланетных тканей, сроки, рецепты и боевые проценты ниже — вымышленные игровые решения. Источники: [Bioprocessing Separations Consortium, DOE](https://www.energy.gov/sites/prod/files/2020/10/f79/beto-biopro-sep-3-year-oct-2020_0.pdf), [исследование хитозанового материала Kompa и Fernandez](https://arxiv.org/abs/2410.10909).

**1. Труп как временный ресурс мира**

- После окончательной гибели создаётся отдельная запись останков: стабильный id, исходный id/тип существа, координаты, семейство сырья, тик смерти/исчезновения и оставшийся выход проб. Существо сразу прекращает движение/атаки; труп не участвует в AI, поиске пути, столкновениях, выборе боевой цели и повторной статистике убийств. Труп можно осмотреть, собрать либо очистить с предупреждением о потере сырья; постройка поверх него не собирает добычу автоматически. Материальная проба, генетическая проба и живые донорские клетки из раздела 3 расходуют один и тот же остаток проб; отдельного бесплатного запаса «крови» поверх туши нет.
- Срок — **игровое время**: одиночная пауза останавливает его, закрытый UI клиента кооператива не останавливает работающий мир. Сохранение/переподключение сохраняют исходный срок, не дают ещё 30–50 минут. В закрытом чанке срок тоже истекает; старый труп не оживает при возвращении игрока. На выделенном сервере таймер идёт вместе с симуляцией, в том числе без игроков при выключенной `pauseWhenEmpty`; серверная пауза останавливает его. На тике истечения сначала закрывается ресурс трупа, затем разрешается завершение сбора: операция, не успевшая до этого тика, не выдаёт пробу и возвращает зарезервированную пустую тару.
- Стартовые сроки и выход герметичных проб: ползун малый **30 мин / 1**, средний **35 / 2**, большой **40 / 4**; плевун **35 / 2**, большой **40 / 4**; панцирник **45 / 6**; разрушитель **30 / 4**; летун **35 / 4**; матка выводка **45 / 8**; гигант **45 / 10**; Королева **50 / 24**. Черви малый/средний/большой/бегемот: **30/35/40/45 мин**, **1/3/6/10** проб. Каждому исходному `k`/прототипу задан собственный предмет пробы, крупный вариант даёт больше сырья своего семейства, а не неограниченно сильный бонус.
- В базовом варианте сохранный труп гарантированно содержит указанный ресурс: случайный шанс редкого выпадения не нужен для запуска цепочки. Элита/мутация не умножает выход по возросшему HP и не создаёт отдельные ранги качества. Самоподорвавшийся разрушитель оставляет обломки с половиной выхода (**2** пробы); обычное убийство до подрыва — **4**. Длительное выжигание либо команда очистки могут удалить ещё не собранные останки, но уже добытые предметы не отзываются.
- У матки и Королевы существующие появления выводка/реакции босса срабатывают один раз при смерти; сбор трупа не вызывает их снова. У уничтоженного червя тело создаёт путь гибели сооружения, а не только `hitUnit`. Гнёзда являются источником территории слизи; разрушенная постройка гнезда не маскируется под дополнительную тушу червя.
- Забор одной пробы занимает **3 секунды**, уменьшает оставшийся выход на один и требует свободного места и одной пустой капсулы. Неполный сбор оставляет остаток в трупе; собранный труп остаётся визуально до исходного срока, но помечен «сырьё извлечено». В панели видны вид, доступные пробы, время до исчезновения и способ сбора. При куче тел список сортируется устойчиво по расстоянию/id.

**2. Отдельный сбор слизи и полевой инструмент**

- Новое действие «Забор биоматериала» с инструментом **биосборник** выбирает труп либо клетку слизи в пределах **2 клеток**. Переназначаемая клавиша/контекстное меню; обычный F для вещей инженера и конвейеров сохраняет прежнее назначение. Полоса процесса обрывается при выходе из радиуса, смене цели или смерти. При отмене до завершения ресурсы не списаны и проба не появляется.
- Пустая капсула: **1 железная пластина + 1 пластик → 5 капсул**, сборщик, **2 с**. Капсула обозначает повторно используемую герметичную тару со стандартной консервацией. В первом варианте собранные герметичные пробы не портятся в сундуках/поездах: таймер относится к неприбранным останкам; дополнительные партии со скрытым возрастом в инвентаре не вводятся. После переработки все капсулы возвращаются пустыми.
- Слизь нельзя получить убийством, наведением карты или из лужи кислоты. За **2 секунды** биосборник удаляет **64** единицы реальной интенсивности клетки и помещает **1 капсулу сырой слизи**. Требуются интенсивность не меньше 64, пустая капсула и место. Например, клетка 230 → 166 → 102 → 38 даёт ровно **3** капсулы; финальная очистка остатка 38 даёт чистую клетку без ещё одной капсулы. Сбор конечного остатка занимает отдельные 2 секунды и не требует тары.
- Изменение проходит тот же слой `creep`, что рост, выжигание, блокировка и отображение карты. Сбор уменьшает действительную территорию; он не оставляет неизменённую слизь как бесконечный предметный источник. Повторный рост рядом с живым гнездом допустим по прежним правилам, но приносит новую слизь только после реального роста. Само присутствие трупа не создаёт слизь; огонь очищает территорию без выдачи ресурса.
- Для автоматизации: **пункт биосбора 3×3**, **120 кВт**, буферы пустых капсул/полных проб, фильтр семейства и зона работ до **24 клеток**; до **4 санитарных роботов** на пункт. Роботы используют реальные полёты, батарею, ёмкость груза и зарядку по модели строительных роботов; везут капсулу к цели и возвращают полную, а не дистанционно телепортируют сырьё. Время извлечения 3/2 с сохраняется. Задание принадлежит конкретному телу/клетке и резервирует только одну операцию; отмена, гибель робота, переподключение и ручной сбор разрешают конфликт без дубликата.
- Пункт не создаёт мгновенную безопасную зону: действующие враги атакуют его и санитарных роботов. Фильтры «только трупы», «трупы и слизь», «очистить тонкую плёнку» позволяют выбирать производство либо зачистку. При полном выходе, отсутствии капсул, энергии или доступного робота работа останавливается с конкретной причиной.

**3. Заводская цепочка и осмысленный выбор фракции**

`Труп → герметичная видовая проба` и `территория Роя → капсула сырой слизи` сходятся в линии:

`очистка слизи → связующий биогель → извлечение выбранной фракции из проб → закрепление в композите → покрытие боеприпаса / биокомпозитный модуль брони`.

- **Очистка:** химзавод отделяет загрязнения и клеточный мусор от слизи; выходит стабильный связующий биогель. Гель помогает распределить и закрепить извлечённые частицы/молекулы, но сам по себе не переносит все способности Роя и не усиливает инженера.
- **Извлечение:** новый **биоэкстрактор 3×3**, **240 кВт**, три раздельных входа жидкостей (вода, биогель, серная кислота), один выход стоков, отдельные предметные буферы и выбор рецепта «семейство → исходный вид пробы → направление I–IV». Используется мягкая промывка/фильтрация для белковых и секреторных фракций, механическое разделение для волокон, отдельная кислотная обработка для минеральной фракции. Сильная кислота не проходит обязательным шагом через все активные белки. В UI видно, какая ткань отбирается и почему подходит выбранному применению.
- **Четыре направления — четыре альтернативных рецепта**, открываемых технологиями, а не четыре полных комплекта бесплатного материала из одной туши. Игрок выбирает рецепт; одна и та же проба не используется одновременно в ветвях I–IV. Другие компоненты данной пробы становятся органическим остатком. Виды большего размера сохраняют идентичные свойства конечного материала, меняя только доступное количество проб.
- **Закрепление:** фракция смешивается с пластиком/металлическим носителем и биогелем по рецепту изделия. Получается стабильный предмет с определённым свойством: например, демпфирующий композит, кислотостойкое покрытие или лёгкая волокнистая подкладка. Сырой орган не вставляется напрямую в магазин оружия или сетку брони. Свойство задаётся полученным материалом/прототипом, не скрытым броском качества.
- **Стоки и остатки:** побочный органический остаток и биологические стоки обязательно учитываются в выходах. Нет места для остатка/стоков — цикл не начинается. Химзавод нейтрализует стоки и связывает осадок в инертный отход; инертный отход и органический остаток уничтожаются отдельным рецептом утилизации в биоэкстракторе за энергию. Обычная вода, кислота и загрязнение не возвращаются бесплатно в замкнутый цикл. Технология утилизации открывается вместе с экстрактором, чтобы первая линия не упиралась в ещё закрытый рецепт.

**Стартовые рецепты:** единицы жидкости — игровые; количества не являются лабораторными инструкциями или моделью сохранения химической массы. Биогель — новая обычная жидкость без температурной энергетики пара.

Модули скорости/эффективности допустимы для переработки; продуктивность запрещена для всех рецептов этой цепочки, включая очистку слизи, извлечение, композиты, покрытия, модули брони, возврат капсул, нейтрализацию и утилизацию. Шаблон рецепта создаёт конечный список прототипов, без динамических произвольных эффектов.

**Проверочный пример материального потока:** четыре пробы дают две фракции и один материал. Для покрытия 10 магазинов нужны **4 пробы + 4 капсулы слизи + 40 воды + 2 пластика + 1 сталь + сами 10 магазинов**; возвращаются **8 пустых капсул**, образуются **3 органических остатка + 20 биостоков** до нейтрализации. Один модуль требует двух таких ветвей, то есть **8 проб и 8 капсул слизи**, а не одну пробу с четырьмя бесплатными бонусами. Дополнительная серная кислота относится только к выбранным минеральным рецептам.

**4. Собственное сырьё и до четырёх направлений для каждого семейства**

Унифицированная капсула хранит **собственный ресурс каждого исходного вида**: например, `bio-sample-small`, `bio-sample-medium`, `bio-sample-big` — отдельные предметы «Проба малого/среднего/большого ползуна». Всего **15** исходных предметов: 11 типов подвижных существ + 4 размера червей. Они не смешиваются в одном рецепте; шаблон создаёт **15 × 4 = 60** конечных рецептов извлечения из конкретной пробы. Внутри одного семейства эти рецепты дают одинаковые четыре направления материала: **9 × 4 = 36** свойств/композитов, без усиления от размера. В каждом столбце указаны **название конечного материала → один активный бонус**. Это выбор дальнейшей переработки, не все четыре эффекта одного модуля.

**5. Совместимость изделий и ограничение бонусов**

- Боеприпас получает **одно биопокрытие** и сохраняет категорию, базовую стоимость/количество выстрелов, совместимость оружия/турели и основную технологическую ступень. Применяются физический/взрывной/огненный материал только к соответствующему основному типу урона; уменьшение разброса — к пулевому/дробовому оружию с действительным разбросом. Материал увеличения радиуса не создаёт взрыв у патрона, а продления огня — пожар у обычной ракеты.
- Вторичная кислота и адгезивное замедление разрешены для пулевых/дробовых/рельсовых боеприпасов, ракет и снарядов; у площадного попадания учитывается один и тот же поражённый объект один раз. Биопокрытия не создаются для лазерной ячейки: органический слой не прибавляет ей энергию. Для каждой пары «исходный боеприпас × направление» есть явный рецепт/прототип и объяснение недоступности остальных.
- Вторичный кислотный компонент равен **3% основного урона выстрела после обычных оружейных исследований, до защиты цели**; его сопротивление считается по `acid` отдельно. Минимальный урон в 1 единицу не применяется к каждому новому малому компоненту: иначе 3% слабого выстрела превращаются в непропорциональную прибавку. Существующий порядок основной плоской/процентной защиты сохраняется; дробь не получает повторную полную прибавку для каждой дробинки вместо своей доли.
- Замедление имеет величину **4%**, а не существующее универсальное сильное замедление. Повторные попадания обновляют срок до 2 с, не суммируют проценты и не замедляют уже движущуюся цель повторным множителем каждый тик. С более сильным старым эффектом выбирается сильнейший, они не перемножаются. На босса действует четверть величины (**1%**); летуны и статичные черви не замедляются.
- Модуль **биокомпозитной подкладки 2×2** устанавливается в существующую сетку брони, пассивен и имеет ровно один выбранный при изготовлении эффект **защиты, скорости инженера либо энергопотребления брони** из таблицы. Направления боеприпасов не превращаются в дополнительную оружейную ауру модуля. Одновременно действует **один** такой модуль на инженера; остальные видны как неактивные. Замена/снятие пересчитывает эффект без накопления. Прибавка скорости добавляется один раз к сумме нормированных бонусов движения (+3% означает +0,03 к этому коэффициенту); уменьшение энергопотребления относится к потребителям оборудования, не создаёт мощность реактора/панелей и не увеличивает ёмкость батареи.
- Снижение входящего урона применяется множителем к остатку после действующих щитов/брони; не добавляет 6 процентных пунктов к уже высоким сопротивлениям. Пример: после обычной защиты осталось 20 урона, подкладка −6% даёт **18,8**, а не полную неуязвимость. Материал Королевы действует только на существующие `phys/fire/laser/expl/elec/acid`, не на экологическую радиацию из раздела 15.2 обновления 1.16.
- Биоэффект не вкладывается в уже биомодифицированное изделие и не объединяется рекурсивно с другими фракциями. Изотопный вариант из раздела 15.2 обновления 1.16 может получить один совместимый биослой, с той же предельной прибавкой к своей базе. Партия покрытия берёт только полные неиспользованные единицы; израсходованные заряды/последний магазин оружия нельзя восстановить рецептом. Переработка/разбор модуля не возвращает больше исходных материалов.
- Бюджет: прямой бонус урона **до 4%**, второй компонент **3%**, скорость **до 3%**, снижение потребления **до 4%**, защита одного типа **до 6%**. Увеличение радиуса/времени не накладывается одновременно с ростом урона от другого биослоя. До финального баланса прогнать оружие против малых целей, панцирника и босса: суммарная эффективность биопокрытия в одинаковом эталонном бою не должна превышать **8%**; недостигнутая цель — причина уменьшить параметр, а не обещать её выполненной.

**7. Сохранения, кооператив, производительность и интеграция**

- Новые состояния предлагаемого формата **19** (после формата 18 в 1.16): записи останков/добычи/сроков, id счётчик, санитарные задания и груз, настройки пункта, прогресс/резервы обработки, конечные прототипы сырья/фракций/композитов/изделий, активный материал брони и точная величина/срок слабого замедления. Интенсивность слизи остаётся тем же сохраняемым слоем мира; декоративные пятна не становятся вторым источником количества. Миграция 18 → 19 не создаёт тела уже давно убитых врагов, сохраняет тела инженеров, исходную слизь и врагов без сброса статистики. Сохранения 1.15 формата 17 проходят последовательную миграцию 17 → 18 → 19; номер 19 окончательно сверяется с выпущенным форматом 1.16.
- Все изменения выполняются в Worker общими командами и проверяют роль/право действия, тип/существование цели, радиус, время процесса, тару, место и фактический остаток. Два игрока/робот с игроком не могут извлечь одну пробу или одни 64 единицы слизи дважды. Заключительная операция списания/выдачи/возврата капсул атомарна; переподключение и повтор пакета идемпотентны. Входящая заявка клиента не задаёт себе произвольный выход, бонус или срок трупа.
- Тела, добыча, задания, жидкости, эффекты и случай возникновения, если его позже добавят, входят в полный/сетевой хеш и снимок позднего входа. Достижения и `cheatsUsed` используют правила раздела 15.3 обновления 1.16; на выделенном сервере полномочия задают его владелец/администраторы. Тестовая палитра может дать биоматериалы для проверки, но это отмеченное тестовое создание; даже в креативе сбор не дублирует один объект.
- Останки группируются для отображения по чанку и близости, с точным доступом к каждому id; сгруппированный спрайт не объединяет количество произвольно. Исчезновение обрабатывает очередь сроков, AI не обходит трупы. Не сокращать обещанные 30–50 минут скрытым удалением после нескольких сотен тел. Стартовая нагрузка — **50 000** действующих трупов, бюджет фонового обслуживания **до 1 мс/тик**, отдельные замеры Worker/отрисовки/сохранения; для ещё большей нагрузки предусмотреть отображение куч и явное предупреждение.
- Диагностика из раздела 15.3 обновления 1.16 показывает «нет проб», «нет биогеля», «нет капсул», «выход отходов заполнен», «цель уже собрана». Группы учитывают добычу/переработку/расход как разные события, не записывают пробу как добытую вновь при её возврате роботом. Оповещения: мало капсул, заполненный пункт, истечение срока отмеченной группы трупов. Планировщик считает ограниченное снабжение пробами и слизью по наблюдаемому сбору, не обещает бесконечные 100 изделий/мин от единственного трупа.
- Справочник RU/EN показывает цепочку, семейство, четыре открытых/закрытых направления, активный бонус и ограничения совмещения. Останки/слизь/очищенная клетка видны согласованно в WebGL2, Canvas и миникарте при одинаковой разведке. Отдельный шаг обучения предлагает собрать обычного ползуна и слизь, получить один композит и сравнить боеприпас/подкладку с исходным изделием; не требует Королеву.

**Приёмка биоматериалов 1.17:**

1. Каждый существующий вид существа и четыре размера червей оставляют один корректный труп; выводок, самоподрыв, огонь, гибель от турели/игрока и уничтожение сооружения червя не дают повторного убийства/добычи. Тело инженера сохраняет прежние вещи и 30 минут.
2. Проверены границы сроков **30 и 50 минут**, пауза, закрытый чанк, сохранение за тик до истечения и поздний вход. Сбор части/всех проб, полный инвентарь, отсутствие тары, отмена и очистка оставляют корректный остаток.
3. Клетка интенсивности **230** даёт ровно **3** капсулы слизи и конечный остаток **38**, очистка остатка не выдаёт четвёртую. Сбор/огонь/рост/граница чанков и конкуренция двух сборщиков изменяют один слой; кислотная лужа не считается ресурсом слизи.
4. Материальный пример выше проходит от исходных проб/тары до 10 полных магазинов либо одного модуля, с точным возвратом капсул и побочными выходами. Переполненный буфер, смешанные семейства, смена рецепта, сохранение незавершённого цикла и попытка продуктивности не создают дополнительный материал.
5. Для всех **15 исходных ресурсов × 4 направления** проверены 60 рецептов извлечения; для всех **9 семейств × 4 направления** — доступность технологии, рецепт материала и хотя бы одно заявленное применение. Статичные черви/летуны/боссы обрабатывают слабое замедление по правилам; два модуля, второе покрытие, дробь, частично израсходованный магазин, кислотоиммунная цель, изотопный патрон и щиты не обходят ограничения.
6. В одиночной партии, реальном браузерном кооперативе до 8 участников и на выделенном сервере до 16 игроков выполнены одновременный сбор одной цели, санитарные задания, гибель робота, переподключение и поздний вход во время переработки/эффекта. Количество сырья/боезапас/возврат капсул и полные хеши совпадают между участниками на контрольных тиках.
7. Сохранённая нагрузка 50 000 трупов не перезапускает AI мёртвых существ, не скрывает случайное удаление ресурсов и имеет отчёт по времени тика/памяти/размеру сохранения. Боевые сравнения подтверждают небольшую прибавку, а не только наличие числа в UI. Эти проверки предстоит выполнить при реализации игры; редактирование ТЗ не доказывает их прохождение.

**Передача биоматериалов 1.17:** готова концепция для прототипа «один ползун → труп → проба + слизь → фракция → физическое покрытие и подкладка». До расширения на все семейства проверить материальный баланс, стоимость сбора, новые поля эффектов/экипировки и кооператив. Затем проверить полный список 36 направлений и зафиксировать проценты/время/цены на основании боевых и производственных измерений.

#### 3. Геномная библиотека и управляемые зеркальные биороботы

**Запрошенная механика:** собирать с трупов кровь/цитоплазму, извлекать ДНК каждого вида, затем через специальное производство создавать его управляемый биологический прототип. Пульт позволяет задать следование за инженером, патруль через точки и переход к точке карты; биороботы сражаются с Роем. Далее — предлагаемые правила и стартовый баланс для прототипа 1.17, а не доступные функции 1.15 или уже выполненные лабораторные/игровые проверки.

**Научная основа и граница игровой условности:**

- Материалом служит **клеточная проба гемолимфы («крови» Роя) либо ткани**, содержащая клетки и их ядра. Цитоплазма сама по себе не заменяет полный ядерный геном выбранной модели организма. Игровые существа Роя здесь моделируются как многоклеточные организмы с ядросодержащими клетками. Для чтения генома достаточно сохраняемой ДНК; для запуска клеточной линии дополнительно нужны жизнеспособные донорские клетки.
- Исследования клонирования показывают использование клеточного ядра и поддерживающей клеточной среды, а не выращивание готового животного из пробирки с очищенной ДНК. В игре это основание для отдельного **банка клеточных линий** и этапа культивирования. [Wilmut и др., Nature, 1997](https://pubmed.ncbi.nlm.nih.gov/9039911/).
- Направленное редактирование генома имеет реальную научную основу, в том числе RNA-направляемые системы Cas9. В игровой лаборатории оно представлено закрытыми технологическими шаблонами совместимости тканей и отсутствия самостоятельного размножения; здесь не задаются реальные последовательности, гены или лабораторные протоколы. [Jinek и др., Science, 2012](https://pmc.ncbi.nlm.nih.gov/articles/PMC6286148/).
- Биогибридные роботы с живой мышечной тканью и искусственными компонентами исследуются в действительности. Это основание для **тканевого тела на поддерживающем каркасе с электронным нейроинтерфейсом**. ДНК не является программой «следуй за игроком» и не передаёт воспоминания убитого врага. [Morimoto, Onoe и Takeuchi, APL Bioengineering, 2020](https://pubmed.ncbi.nlm.nih.gov/32266324/).
- Полноразмерные боевые копии Роя, универсальная совместимость инопланетных клеток, выращивание за игровые минуты и управление сложным поведением — **научно-фантастические допущения**. Клонирование, чтение генома, редактирование клеточной линии, выращивание тканей и электронное управление показаны как разные этапы, а не одна мгновенная операция извлечения ДНК.

**1. Полевой сбор: генетический материал и донорские клетки**

- После исследования клеточного сбора у существующего биосборника появляются режимы **«Материал»**, **«Генетическая проба»**, **«Живые клетки»**. Все расходуют по одной доступной пробе трупа; режимы генетики дополнительно требуют одну пустую капсулу и один набор консервации. Длительность 3 с/пробу и радиус 2 клетки сохраняются. Забор слизи остаётся отдельной операцией; лужа кислоты не выдаёт геном.
- Генетическую пробу можно собрать до общего исчезновения трупа через 30–50 минут. Живые донорские клетки — только в первые **10 игровых минут** после смерти; это предлагаемый игровой порог жизнеспособности, не универсальная биологическая константа. Полностью выжженный труп/самоподорвавшийся разрушитель не дают живые клетки; сохранившиеся обломки разрушителя допускают генетический материал в пределах его оставшегося выхода. Убитый до подрыва разрушитель может дать оба типа проб по выбору.
- Генетические и клеточные пробы — два разных набора конечных предметов по **15 исходным видам**. Они не смешиваются между видами, не подменяют друг друга и не создаются из уже переработанной фракции/композита. Срок допустимости живого сбора проверяется при завершении операции, до выдачи предмета; таймер не обновляется повторной командой или загрузкой.
- Клеточный режим обозначает немедленную консервацию в полевой капсуле. В версии 1.17 **у уже собранных консервированных проб нет скрытого инвентарного таймера**: стабильная сохранность капсулы — явное упрощение игры. Она не означает бесконечное питание выращенного организма; работа банка/фабрикатора и обслуживание живых биороботов учитываются отдельно.
- Пункт биосбора и санитарные роботы получают фильтр вида и режима, видят приближающийся срок живого сбора. Резервирование общей пробы не позволяет роботу и игроку одновременно выдать материал и живые клетки. Трупы инженеров и дружественных биороботов не являются источником геномов Роя.

**2. От анализа ДНК к управляемому телу**

`Клеточная проба → отделение клеток/выделение ДНК → чтение и сборка генома → запись видового шаблона`.

Параллельная ветвь: `живые донорские клетки → первичная клеточная линия → банк и размножение культуры за питательную среду`.

Обе ветви сходятся: `геном + культура того же вида → подготовленная клеточная линия → выращивание тканей на каркасе → нейроконтроллер → проверка и выпуск союзного биоробота`.

- **Генетическая лаборатория 3×3, 480 кВт на активную обработку сверх хранения** выполняет анализ/сборку и хранит живые линии. Имеет три раздельных входа (вода, биогель, среда) и выход биостоков. Общая видовая библиотека принадлежит миру, содержит до 15 записей и доступна по действующим правам партии. Каждая запись открывается чтением проб **конкретного вида**, а не автоматически от родственного малого ползуна. Сведения из энциклопедии не равны изученному геному.
- Геном — сохраняемая информационная запись, не расходуемый ингредиент каждого экземпляра. При уничтожении лаборатории изученные записи сохраняются; конкретные живые культуры, материалы и прогресс разрушенного здания теряются по обычным правилам. Миграция старого мира не выдаёт автоматически ДНК всех уже убитых существ.
- Живые линии привязаны к лаборатории/виду: стартовый запас 2 условные порции после основания, ёмкость **100 порций на линию**. Деление культуры тратит среду, воду, время и энергию; из одной порции делает две, то есть прирост **одна**, без бесплатного побочного выхода. На экспорт оставлять минимум одну материнскую порцию. Для перевозки снимается настоящая порция и расходуется пустая капсула; возвращённая тара не восстанавливает клетки.
- Режим хранения требует **20 кВт на лабораторию + 5 кВт на действующую линию**. При отсутствии питания выращивание/выдача приостанавливаются; после **15 игровых минут** непрерывного нарушения линия утрачивается с предупреждением заранее. Это предлагаемый баланс хранения; цифровой геном не стирается. Сроки сохраняются и подчиняются серверной паузе, а не часам браузера.
- **Биофабрикатор 6×6, 1,2 МВт**, с входами воды/биогеля/питательной среды, выходом биостоков и свободной площадкой выпуска, выращивает одну особь за цикл. Фазы: резервирование → подготовка клеточной линии → тканевое выращивание на каркасе → установка/калибровка нейроконтроллеров → готово → выпуск. Размер и разновидность выбираются из изученных геномов с открытой технологией.
- Один экземпляр имеет исходный вид, стабильный id, владельца, фракцию игрока и ссылку на свою базовую форму. Очередь до **5** работ на фабрикатор. Энергия/жидкости и ингредиенты действительно потребляются; при нехватке конкретный этап останавливается. Ключевые расходные позиции резервируются до начала, переработанное тело не возвращается в исходные клетки при отмене. Возвращаются только неиспользованные резервы; готовый/частичный организм не выдаёт вторую копию ингредиентов.
- Готовая особь выпускается только на проверенную свободную площадку и остаётся привязана к фабрикатору до появления в мире. Нельзя получить одновременно предмет «готовый робот» и действующего юнита. Готовые, растущие и действующие особи занимают единый лимит; заблокированный выход не позволяет накопить неограниченную армию внутри машин.

**Стартовые игровые рецепты:** условные количества для экономики; не лабораторные составы. Питательная среда — новая жидкость из переработанного органического остатка первой механики, биогеля и воды; газовая/аграрная отрасль не вводится ради этой ветви, подача отфильтрованного воздуха входит в оборудование и энергопотребление зданий.

Несколько контроллеров крупного тела являются узлами одного нейроинтерфейса. 90W среды уходят на выращивание, **10W сохраняются внутри как стартовый запас питания на 5 минут**, не появляются поверх оплаченных 100W. Для червей дополнительно расходуются **5W шестерней + W двигателей** на транспортную опору. Нейтрализация/утилизация стоков используют правила раздела 2. Продуктивность запрещена для анализа/банка/культуры/нейроконтроллеров/выращивания и фасовки питания; ускорение не создаёт бесплатные клетки, еду или дополнительные юниты.

Генолаборатория: **30 стали + 20 продвинутых схем + 10 процессоров + 10 труб**. Фабрикатор: **60 стали + 100 бетона + 20 процессоров + 20 труб**. Командный пункт: **20 стали + 10 процессоров + 5 батарей**. Пульт/нейромодуль: **5 процессоров + 5 продвинутых схем + 2 батареи**. Сопоставить рецепты с фактическими id ингредиентов 1.15; новые названия выше являются предлагаемыми прототипами. Три жидких входа фабрикатора раздельны, биостоки не смешиваются со средой.

**Пример:** для малого ползуна W=1 требуется 2 капсулы его живой культуры, 5 стали, 4 пластика, 1 контроллер, 100 среды, 100 воды и 20 биогеля; базовое выращивание — **40 с**, активная энергия фабрикатора — **48 МДж** до модулей. Выходит один ползун, две пустые капсулы и 100 биостоков, внутри остаётся 10 питания. Для создания двух запасных культур из минимальной материнской порции нужно два оплаченных деления, затем экспорт двух порций с сохранением одной в банке.

**3. Зеркальные виды, масса управления и ограничения поведения**

Зеркальный прототип сохраняет узнаваемые форму, размер, способ передвижения, обычную боевую роль, базовые HP/урон/сопротивления **немутировавшего** исходного вида. Отличия видны по цвету партии, нейроинтерфейсу и маркеру союзника. Архив не копирует накопленную эволюцию, элитные множители, мутационные уровни или состояние погибшего противника. Проценты улучшений обычного оружия инженера не усиливают автоматически живую атаку. Все 15 прототипов имеют конкретное соответствие исходным id.

| Исходный вид | W | Роль и особое правило союзного прототипа |
|---|---|---|
| `small` / `medium` / `big` | 1 / 2 / 4 | Наземный ближний бой, те же три формы ползуна |
| `spitter` / `spitter-big` | 2 / 4 | Дальняя кислотная атака; дружественные лужи сохраняют принадлежность и не разъедают свою базу |
| `armored` | 6 | Панцирник: медленный защищённый передний ряд |
| `destroyer` | 4 | Разрушитель; самоподрыв выключен по умолчанию и разрешается отдельным приказом конкретной особи с 2 с подготовки |
| `flyer` | 4 | Летун: полёт по правилам оригинала, не превращает весь отряд в проходящий сквозь стены |
| `brood` | 8 | Матка: её собственная атака; рождение выводка и появление живых юнитов при смерти отключены |
| `giant` | 10 | Гигант: тяжёлый ближний бой; широкому телу нужен действительно проходимый маршрут |
| `queen` | 24 | Зеркальная Королева: один экземпляр **на мир**, включая растущую/готовую; не порождает маток, гнёзда и эволюционные мутации |
| `worm-small` / `worm-medium` / `worm-big` / `worm-behemoth` | 2 / 4 / 6 / 10 | Червь на складываемой транспортной опоре; в движении не атакует, развёртывание/сворачивание по 5 с |

- Стационарный червь не получает магические ноги из изменения ДНК. Перемещение обеспечивает оплаченный механический носитель; в точке он разворачивается и использует исходную дальность/атаку. В режиме следования носитель едет за инженером, а для боя останавливается/разворачивается; для патруля перемещается между точками с теми же ограничениями размеров/маршрута.
- Стартовые лимиты: **24 W на игрока**, **128 W на мир браузерного кооператива**, **256 W на выделенный сервер**, максимум **4 отряда на владельца**. Одиночный игрок также имеет 24 W. Если общий лимит меньше суммы личных, UI показывает оставшийся общий бюджет. Производство заранее резервирует W; изменение владельца, ручной выпуск и несколько фабрикаторов не обходят предел. Все значения подлежат проверке баланса/нагрузки, а не считаются доказанными характеристиками версии.
- Банк клеток может размножать клетки за питание, но сами боевые организмы **стерильны в игровой модели**: не создают новый Рой, слизь, яйца, маток, гнёзда или потомство при гибели. Они не превращаются во враждебных после отключения пульта. Потеря экземпляра освобождает его W один раз; автоматическая замена возможна только новой оплаченной работой фабрикатора.
- Останки союзного биоробота дают ограниченный органический лом, но **не донорские клетки, не видовой генетический экстракт и не обычный ресурс трофея Роя**. Стартовый выход — W органических остатков, остальные контроллеры/ткань потеряны. Нельзя выращивать собственных маток/Королев для бесплатного генома/сырья/потомства. Убитые ими настоящие враги оставляют обычные трофеи, что является результатом боя с Роем.

**4. Пульт и команды отряда**

- После исследования управления доступны **командный пункт** с постоянным питанием **150 кВт** и переносной **биопульт** через модуль 2×2 сетки брони, **20 кВт при управлении**. Это UI отряда, не дополнительные произвольные строки JS/консоли. Игрок выделяет своих биороботов рамкой/списком, создаёт именованный отряд, видит состав, W, HP, питание, текущую команду, связь и предупреждения.
- **«Следовать за инженером»** выбирает конкретного участника партии, держит строй с интервалом и базовым расстоянием 3–8 клеток. Отряд обходит постройки/других участников, не заталкивает инженера в воду и не телепортируется при его перемещении. Переход к другому инженеру задаётся явной командой владельца.
- **«Патрулировать»** задаёт **2–16 точек** на разведанной карте, порядок и режим замкнутого круга/туда-обратно. До подтверждения видны линия, проблемные участки и стоимость маршрута по времени. Юниты проходят маршрут, вступают в допустимый бой и возвращаются к текущей точке/индексу после завершения. Изменение карты повторно проверяет путь; заблокированная точка показывает причину, не перескакивается как выполненная.
- **«Идти к точке»** отмечает позицию на карте и выбирает «идти без поиска боя» либо «идти с боем». В первом варианте отряд отвечает на непосредственную атаку, во втором атакует встреченный Рой в пределах своей зоны преследования. Достигнув точки, удерживает её; игрок может назначить новую. Дополнительные короткие команды: остановиться, удерживать, вернуться к своему пункту снабжения, разрешить/отменить подрыв разрушителя.
- По умолчанию цель — **только Рой: вражеские юниты, черви и гнёзда**. Агрессивное преследование ограничено 24 клетками от маршрута/защищаемого инженера/точки; затем возврат. Союзники, персонажи, собственные строения и дружественные биороботы не являются целью. Урон/лужи/взрывы сохраняют фракцию источника; безопасный режим партии не позволяет биороботу обойти запрет дружественного урона. Самоподрыв — необратимая потеря конкретной особи, не дополнительная бесплатная атака с последующим возвратом тела.
- Для новой команды нужна связь с питаемым пунктом/пультом в **128 клетках**; пункты в этом радиусе образуют простую ретрансляционную цепь. Команда отправляется один раз, маршрут выполняется автономно: потеря связи не отменяет уже принятый патруль/переход. Вне связи UI показывает время последнего сведения и не позволяет менять приказ. Ни туман, ни последнее известное положение врага не становятся достоверной текущей целью; реальный отряд открывает карту только своей действительной разведкой.
- При отключении владельца следование через **30 игровых секунд** заменяется возвратом к назначенному пункту либо удержанием последней безопасной точки, если пункта нет. Патруль/удержание продолжаются до нового разрешённого приказа, ограничений питания или маршрута. Администратор может передать отряд другому участнику; простая замена индекса подключившегося игрока не меняет владельца автоматически.

**5. Питание, содержание и утрата условий**

- Организм потребляет **2W единицы среды в минуту** действующего игрового времени; запас до **10 минут**, начальный — 5 минут, оплачен при выращивании. Питательная капсула содержит ровно 20 единиц; при передаче её содержимое переносится в запас до свободной ёмкости, тара возвращается один раз после полного использования. Остаток неполной капсулы сохраняется, не превращается в новую полную упаковку.
- Командный пункт имеет настоящие запасы питания и обслуживает назначенных особей в пределах **8 клеток**; логистика привозит капсулы обычным способом. При остатке менее **2 минут** отряд предупреждает и по настройке возвращается на снабжение. Полный пункт, разрыв маршрута и пустой запас показываются как разные причины. Переименование/смена группы не наполняют резерв и не лечат организм.
- При нулевом питании биоробот прекращает бой и передвижение; через **120 секунд** начинает терять **1% своего максимального HP в минуту** до снабжения. Это игровая упрощённая модель истощения, не реальная физиологическая норма. Он не становится врагом. Потеря связи и отсутствие питания — разные состояния; работающий на сервере мир продолжает расход/таймеры, а серверная пауза останавливает их.
- В пункте при отсутствии боя 30 с возможен ремонт тканей: **1% максимального HP за 10 с**, дополнительно **5W среды за такой шаг**. Он не тратит ДНК и не регенерирует бесплатно в полевом бою. Готовая особь в заблокированном фабрикаторе также остаётся живой, занимает W и требует оплаченного питания; готовность не замораживает расходы навсегда.

**7. Данные, AI, сохранения и кооператив**

- Предлагаемый формат 1.17 остаётся **19**, вместе с первой биомеханикой: добавляются источники/режимы проб, библиотека 15 геномов, реальные банки/их сроки и порции, питательная среда/тара, резерв W, фазы фабрикатора, тело/HP/состояние особи, стабильный владелец, фракция, питание/остатки расхода, нейроинтерфейс, отряд/точки/индекс маршрута, связь, назначенный пункт, транспортная опора червя и подготовка подрыва. Не нужен ещё один номер формата для второй части невыпущенного обновления.
- Миграция старого мира даёт пустую библиотеку, нулевые культуры и отсутствие союзных биороботов; прежние враги, трупы/слизь, исследования и собственность сохраняются. Геномы принадлежат миру, живые банки — конкретным зданиям, особи/приказы — стабильным идентификаторам участников. Поздний вход, передача хоста, смена индекса игрока и открытие сетевого мира в одиночку не дублируют собственника/отряд.
- Нельзя поместить союзника в существующий массив `g.units` и ожидать правильной фракции: старые селекторы рассчитаны на Рой. Добавить явную принадлежность в общую модель целей либо отдельную коллекцию союзных особей с интеграцией пространственного индекса; проверить турели, попадания, взрывы, лужи, AI Роя, статистику и тела. Рой должен уметь атаковать биороботов; игрок и своя оборона — распознавать союзников. Шаблон пути учитывает размер, полёт и носитель червя.
- Приказы проходят общий авторитетный путь Worker/сервера: проверяются владелец/роль, доступная связь, id/фракция/жизнь целей, конечные координаты, разведка, до 16 точек, лимиты W и существование пункта. Состав отряда и геном не задаются произвольным исполняемым кодом/последовательностью. Обычный клиент не повышает параметры из локального поля и не управляет чужим отрядом; администратор явно передаёт права общей командой.
- Сортировка событий/особей/конфликтов стабильна, изменения применяются на границе тика. Расход жидкости/пищи и малый урон истощения имеют сохраняемые остатки, не зависят от FPS. Полные/сетевые хеши и снимки включают все значимые состояния; оптимизируемый кэш маршрута не заменяет приказ/позицию/индекс. Повтор сообщения не выпускает вторую особь и не возвращает повторно тару/резерв W.
- В редакторе явно разделить союзную особь, исходного врага, изученный геном и существующую живую культуру. Для новых полей сценария предложить **`fmt: 3` после `fmt: 2` версии 1.16**, с миграцией прежних сценариев без выдачи геномов/армии; номер сверяется с выпущенным форматом. Сценарные запреты типов/технологий и тестовая отметка не обходятся через фабрикатор.
- Диагностика показывает «геном не изучен», «нет живой линии», «не хватает среды», «резерв W исчерпан», «выход занят», «нет связи/пути/питания». Оповещения предупреждают об утрате банка, питании отряда, потерях и блокировке производства; группы учитывают рост/обслуживание отдельно от трофеев, планировщик рассчитывает культуры/контроллеры/энергию/содержание по W. UI/подсказки и обе ветки рендера доступны RU/EN.
- Нагрузка отдельно измеряется для **128 W браузерной партии и 256 W сервера**, смешанного отряда, очередей путей, 16 владельцев и первой механики с 50 000 трупов. Пространственные индексы, переиспользование пути отряда и распределённые по тикам задачи заменяют полный обход каждого существа/карты. Отчёт содержит время тика/память/размер снимка; выбранные лимиты уменьшаются при подтверждённом провале бюджета, не объявляются выполненными по наличию UI.

**Приёмка второй механики 1.17:**

1. Все 15 исходных видов имеют собственные генетические/клеточные пробы, запись и выращиваемый зеркальный прототип. Проверены общий остаток трупа, живой сбор до/на границе 10 минут, общий срок 30–50 минут, выжигание, подрыв, санитарный робот и одновременный сбор двух игроков без дополнительного бесплатного сырья.
2. Из проб прочитан геном, из отдельной живой пробы основана линия, оплачены деление/экспорт и выращен первый ползун. Проверочный рецепт W=1 даёт одну особь/48 МДж/две пустые капсулы, не бесплатную ДНК-армию. Потеря питания/банка, полный выход стоков, отмена на каждой фазе и загрузка посреди процесса сохраняют точные ресурсы/стадии.
3. Следование за каждым выбранным инженером, патруль 2–16 точек и переход к точке с обоими правилами боя работают на карте с водой, стенами, узким проходом и изменившейся постройкой. Летун и транспорт червя имеют правильные маршруты; недоступная точка/потеря связи объясняется, не маскируется телепортом.
4. Рой сражается с союзной армией, своя оборона распознаёт её фракцию. Проверены кислота/взрыв/площадной урон, исходные сопротивления, стерильность матки/Королевы, подрыв разрушителя и недопустимость генетических трофеев со своих особей. Базовые показатели не получают элитные/мутационные множители или четыре бесплатных свойства материала.
5. Пища, неполная капсула, стартовые 10W, снабжение, истощение и ремонт не создают лишнюю среду/тару. Проверены 24 W владельца, 128/256 W мира и единственная Королева с учётом растущих/готовых особей, одновременных фабрикаторов, смены владельца и повторной команды выпуска.
6. В одиночке, браузерном кооперативе и на сервере с 16 участниками пройдены конкурирующие приказы, чужой отряд, выход владельца, поздний вход, передача/перезапуск сервера, пауза и продолжение. Полные хеши совпадают между участниками; ресурсы, стаи/индексы маршрута, питание и W не дублируются.
7. Смешанная армия на заявленном пределе и большой слой трупов имеют измеренный нагрузочный отчёт; прежняя оборона, враги, сценарии и первая биомеханика проходят регресс. Параметры экономики/Королевы/радиосвязи подтверждены боевыми и производственными прогонами. Это будущие проверки реализации; текущая правка фиксирует концепцию, а не утверждает создание работающих биороботов.

**Передача второй механики:** первый прототип — три пробы малого ползуна (две на геном, одна живая на банк), основание линии с двумя порциями, одно оплаченное деление до трёх/экспорт двух с сохранением материнской порции и одна особь с командой следования. Затем патруль/точка, враждебные цели и кооператив; после подтверждения ресурсов/фракции/путей — все 15 форм, носители червей и ограниченная Королева.

#### 4. Программируемый громкоговоритель для схемотехники

**Назначение:** игрок строит громкоговоритель, выбирает звук и условие включения через красный/зелёный провод. Звук слышен рядом с постройкой либо по всей карте текущего мира. Основной пример — сирена при нападении; та же постройка сообщает о низком запасе топлива, заполненном складе или остановке производства по доступным сигналам схемы.

**Исходная база и границы:** в 1.15.0 уже есть технология `circuit-network`, провода, комбинаторы, проверка условий и клиентский `GameAudio` с общими/позиционными эффектами. Программируемого громкоговорителя и проводного выхода радара с сигналом нападения в этой базе нет: оба описаны ниже как новые требования 1.17. Звуковые пресеты встроены в игру; загрузка аудиофайлов, музыка из сети и музыкальный секвенсор в объём этой механики не входят. Числа рецепта, питания, радиуса и ограничений — стартовые предложения для проверки при реализации.

**1. Постройка и доступность**

- Предмет/постройка `programmable-speaker` («Программируемый громкоговоритель»), размер **1×1**, электрическое питание. Стартовый рецепт: **5 стальных пластин + 5 медных пластин + 5 электронных схем**, **5 с**, изготовление инженером или сборщиком по обычным правилам. Открывается существующей технологией **«Схемотехника»**; после миграции мира с уже изученной технологией рецепт доступен без повторного исследования.
- Потребление: **1 кВт** в ожидании, **5 кВт суммарно** при воспроизведении. Работа требует полного питания текущей фазы; при его потере сигнализация прекращается. Можно назначить приоритет питания через систему 1.16, чтобы сохранить сирену при дефиците энергии; радар и комбинаторы цепочки также требуют питания.
- Одна входная клемма принимает красную и зелёную сети. Значения одного сигнала складываются по существующим правилам схемотехники; отсутствующий сигнал равен нулю. Постройка не выдаёт собственный звуковой сигнал обратно в провод. Режим по умолчанию — «Выключен», чтобы новая постройка не включалась без настройки.

**2. Окно настроек и режимы звука**

| Настройка | Поведение |
|---|---|
| Источник включения | «Выключен», «Вручную включён» или «Условие сети»: выбранный сигнал сравнивается с числом/другим сигналом штатными операторами схемотехники. |
| Звук | Встроенные пресеты: сирена нападения, короткая тревога, звонок, низкий предупреждающий гудок и сигнал завершения. |
| Область | **«Рядом»** — звук от координат постройки; **«Вся карта»** — слышат все подключённые игроки текущего мира независимо от позиции. |
| Радиус местного звука | **8–64 клетки**, по умолчанию **32**; используется только для области «Рядом». |
| Громкость | **0–100%**, по умолчанию **60%**; дополнительно умножается на личную громкость оповещений и общую громкость игрока. |
| Воспроизведение | «Один раз при включении», «Повторять, пока включён» или «Непрерывно, пока включён». |
| Интервал повтора | **1–60 игровых секунд**, по умолчанию **5 с**, отсчитывается между началами коротких сигналов. |
| Пауза между срабатываниями | **1–60 игровых секунд**, по умолчанию **5 с**; применяется к новым включениям, в том числе при дребезге условия. |
| Подпись и группа тревоги | Подпись до **64 символов**, например «Атака с севера»; необязательная группа до **32 символов** для объединения одинаковых тревог. Пустая группа означает отдельный источник. |
| Визуальное оповещение | Переключатель: значок громкоговорителя на карте, его подпись и место для перехода камеры. По умолчанию включено. |

- Для «Рядом» расстояние считается **от инженера слушателя**, а не от камеры. В центре действует выбранная громкость, к границе радиуса она линейно падает до нуля; за радиусом звук отсутствует. Панорама зависит от положения источника. Просмотр удалённого участка карты не переносит инженера и не позволяет услышать местную сирену издалека. «Вся карта» не имеет затухания/панорамы и относится только к текущей партии.
- «Один раз» запускается на переходе эффективного состояния из выключенного во включённое. «Повторять» даёт первый сигнал на этом переходе, затем повторяет его с выбранным интервалом. «Непрерывно» поддерживает цикл выбранного пресета без запуска новой копии каждый тик. Плановый повтор, пришедший до завершения предыдущего короткого сигнала той же группы, пропускается без очереди/наложения. Пока условие ложно, звук прекращается; короткий сигнал мягко обрывается, цикл останавливается. При повторном включении до окончания паузы новый старт пропускается, а не откладывается в очередь. Новый переход после паузы разрешён; продолжающийся режим повтора/цикла может возобновиться, когда пауза закончилась и условие всё ещё истинно. Пауза между срабатываниями ограничивает новые включения, а интервал повтора — плановые повторы уже включённого источника.
- Эффективное включение требует команды/истинного условия, исправной постройки и полного питания. Потеря питания, демонтаж, уничтожение или смена режима на «Выключен» останавливают звучание. Восстановление питания считается новым включением с учётом паузы; загрузка сохранения и поздний вход сверяют текущее состояние, но сами не создают новое включение.
- Кнопка **«Прослушать»** проигрывает пресет один раз только у нажавшего игрока, с его настройками громкости; не передаёт звук остальным и не меняет условие, таймеры или состояние мира. Копирование настроек и чертежи сохраняют конфигурацию, но не переносят активное звучание/таймеры старой постройки; новая копия начинает с выключенного логического состояния.

**3. Сигнал нападения: проводной выход радара**

- У существующего радара добавить подключение красного/зелёного провода и режим **«Читать угрозы»**. Стартовый радиус наблюдения — **32 клетки**, настройка **8–64**; он дополнительно ограничивается фактической областью наблюдения радара. Сигналы формируются только по обнаруженным в этой области враждебным живым существам. Дружественные биороботы, останки и неизвестные существа за пределами наблюдения не считаются врагами. Радар не получает сведения об атаках из неразведанных частей карты.
- Выход `signal-enemy-count` («Обнаруженные враги») — количество таких существ в радиусе. Выход `signal-attack-active` («Нападение») — **1**, если хотя бы одно обнаруженное враждебное существо находится в состоянии штурма/атаки с текущей целью на игроке, дружественной постройке или биороботе; иначе **0**. Движение к выбранной цели в фазе штурма тоже считается нападением. Обнаруженный урон от врага по дружественной цели в наблюдаемом радиусе удерживает этот выход на 1 ещё **5 игровых секунд** после последнего попадания, чтобы сирена не мигала при смене целей. Это текущее состояние/ограниченный таймер, а не наличие старой записи в журнале атак.
- При отключении режима, потере питания или удалении радара выходы равны нулю, таймер удержания очищается. После восстановления питания состояние угроз вычисляется заново; исторические нападения не запускают сирену. Новые виртуальные сигналы доступны в штатном выборе сигналов комбинаторов/условий. Цикл «наблюдение → сеть → условие громкоговорителя» имеет определённый порядок обновления; при прямом проводном соединении задержка после обнаружения — не более одного цикла схемотехники, комбинаторы добавляют свою штатную задержку.
- **Пример схемы:** радар с «Читать угрозы» → красный провод → логический комбинатор с условием `Нападение > 0`, выход `signal-A = 1` → провод с выходной клеммы комбинатора → громкоговоритель с условием `A > 0`, пресетом «Сирена нападения», областью «Вся карта» и непрерывным воспроизведением. Подпись «Нападение на северную базу», группа `base-attack`. Для одной простой тревоги разрешено соединить радар напрямую с громкоговорителем и проверять `Нападение > 0` без комбинатора.
- Несколько радаров могут питать одну сеть: их двоичные выходы складываются, поэтому условие `Нападение > 0` сохраняет смысл. Общая сирена может включаться от любого из наблюдаемых участков; местная сирена с отдельной сетью обслуживает свой участок. Короткая базовая тревога игры и настраиваемые оповещения 1.16 продолжают работать по своим правилам; громкоговоритель предоставляет строительную схему для пользовательского звука.

**4. Несколько тревог, интерфейс и личные настройки**

- Одинаковые активные сигналы с общей непустой группой, пресетом, областью и режимом воспроизведения объединяются для каждого слушателя: один звук и одно визуальное сообщение с количеством источников. Для местного звука берётся самый громкий из слышимых источников, для общего — наибольшая настроенная громкость; громкости не суммируются. Отключение одного источника не гасит другие. Новый источник в уже звучащей группе не перезапускает цикл. Разные пресеты/области/режимы остаются разными тревогами.
- Стартовое ограничение на клиенте — **не более 4 одновременно слышимых групп громкоговорителей**; первым звучит пресет сирены нападения, затем остальные по слышимой громкости и стабильному id. Ограничение аудио не удаляет логические тревоги и значки; после освобождения места продолжающиеся циклы/повторы могут стать слышимыми. Пропущенные короткие сигналы не образуют очередь и не проигрываются позже.
- В настройках звука добавить личную громкость **«Громкоговорители»** и отключение этой категории. Это локальное предпочтение: настройка постройки и слышимость других участников не меняются. Визуальные оповещения доступны при отключённом звуке. В окне постройки видны фактические входные значения, результат условия и статус: «Выключен», «Нет питания», «Ожидание сигнала», «Пауза между срабатываниями» или «Активен».
- Если клиентская аудиосистема ещё не активирована или недоступна, состояние тревоги/значок сохраняются. После активации звука воспроизводится только актуальный непрерывный режим или следующий плановый повтор; накопленные звуки не догоняются. Общая пауза мира останавливает звучание и игровые таймеры, продолжение восстанавливает актуальные циклы. Закрытое окно настроек не останавливает работающую сигнализацию.

**5. Одиночная игра, кооператив, сервер и сохранения**

- Условие, питание, переходы состояния и таймеры определяет авторитетная симуляция: локальная в одиночке, хост в браузерном кооперативе, выделенный сервер в серверной партии. Изменение настроек идёт через обычную команду взаимодействия с постройкой с проверкой прав и диапазонов. Клиенты не рассылают самостоятельные «глобальные звуки» и не создают тревоги по своей копии мира.
- Для короткого сигнала передаётся событие со стабильным id, тиком и id источника; для цикла — текущее состояние/его изменения. Повторно доставленное событие не даёт второй звук. Поздний вход получает активные тревоги и текущие циклы, но не воспроизводит историю коротких сигналов; после переподключения используется тот же порядок. Сервер без интерфейса рассчитывает состояния и отправляет события, сам аудио не воспроизводит. Область «Вся карта» охватывает участников текущего мира, включая удалённых инженеров, в одиночке, браузерной партии до 8 игроков и серверной до 16.
- В планируемом формате сохранения **19** хранить настройки громкоговорителей/радаров, результат прошлого условия, эффективное включение, таймеры повторов/паузы и удержания нападения. Подключения входят в обычную проводную сеть; логическое состояние включено в синхронизацию и контрольный хеш. Клиентские аудиоузлы, личная громкость и список проигранных эффектов не являются состоянием мира. Дополнительное повышение формата до 20 для этой механики не требуется.
- Загрузка/перезапуск восстанавливают активные циклы после подключения слушателя, следующую дату повтора и оставшуюся паузу; завершённые одиночные сигналы повторно не создаются. В новом клиентском сеансе дедупликация опирается на текущий снимок и границу его событий. Радар проверяет актуальную видимость перед выдачей сигнала, его сохранённый таймер остаётся ограничен исходным сроком. Миграция из предыдущего формата сохраняет прежние постройки/провода, добавляет выключенное чтение угроз радарам и не создаёт громкоговорители автоматически.

**6. Приёмка механики громкоговорителя**

1. Изготовление/исследование/миграция, питание, оба цвета проводов, сумма сигналов, отсутствующий сигнал, штатные сравнения и копирование настроек работают; чертежи создают новые независимые источники.
2. Для режима «Рядом» проверены центр, промежуточное расстояние, граница/выход за радиус и независимость от камеры. Для «Вся карта» два игрока на противоположных концах мира слышат одну тревогу; другой мир не получает её. Громкость постройки и личные настройки применяются совместно.
3. Все три режима проверены на первом переходе, длительном истинном условии, частом переключении, окончании паузы, потере/возврате питания, демонтаже и уничтожении. За один переход не возникают новые копии каждый тик; после отключения звук не остаётся играть.
4. Пример с радаром действительно включает сирену при обнаруженном штурме и выключает после завершения/5-секундного удержания. Пассивный враг даёт только число врагов; биоробот/труп/невидимый враг не создаёт сигнал нападения. Исторический журнал атак не служит постоянным источником тревоги; два радара корректно суммируются.
5. Объединение источников, отключение части группы и лимит 4 звуков не дают накопления громкости/очереди; визуальные предупреждения остаются доступными при молчании. «Прослушать» слышит только нажавший игрок.
6. В одиночке, браузерном кооперативе и серверной партии проверены общая пауза, поздний вход, повторная доставка, переподключение, сохранение/загрузка и перезапуск сервера. Хеши логического состояния совпадают; старые короткие сигналы не повторяются, актуальные циклы/таймеры восстанавливаются. Проверен клиент без активного аудио; сервер работает без браузерного звукового API. Это критерии будущей реализации, а не утверждение о готовом громкоговорителе.

#### 5. Ближний бой: шесть видов оружия от старта до поздней игры

**Замысел:** инженер получает дешёвое оружие для первых встреч, затем выбирает между дистанцией, ударами по группе, контролем и пробиванием панциря. Поздние виды требуют развитой промышленности и расходуют энергоячейки. У каждого оружия есть сильная сторона и ограничение: высокая цена не делает его лучшим во всех боях. Ближний бой дополняет огнестрельное оружие и оборону базы; подход к плевунам, разрушителям и боссу остаётся опасным.

**Исходная база:** в архиве 1.15.0 есть оружейные слоты инженера, интервалы атак, типы урона `phys/fire/laser/expl/elec/acid`, сопротивления врагов и `laser-cell` с **20 зарядами**. Отдельного ближнего боя и удара кулаком нет: без оружия `playerShoot` предлагает изготовить пистолет. Все шесть прототипов, их контактные атаки и особенности ниже — новое предложение 1.17. Числа являются стартовым балансом; расчёт по защите 1.15 подтверждает различия, но не заменяет игровые прогоны.

**3. Защита врага и проверочный расчёт эффективности**

- Для обычного компонента сохраняется порядок 1.15: `урон = max(1, D − F) × (1 − R)`. Для `phys` берётся полная плоская защита `F`; для `fire/elec` плоская защита равна 0. `R` — явное сопротивление этому типу, если оно задано; иначе `pct` для физического и `pct/2` для огненного/электрического. Явное сопротивление **заменяет** значение по умолчанию, не перемножается с ним второй раз. Каждый положительный основной компонент дубинки обрабатывается отдельно.
- Виброклинок на обычной цели использует **40% плоской защиты** и **50% положительного физического сопротивления**: `F′ = 0,4F`, `R′ = 0,5R`. Отрицательное сопротивление/уязвимость не ослабляется. На боссе сила пробивания вдвое меньше: `F′ = 0,7F`, `R′ = 0,75R` при положительном `R`. Свойство действует на этот удар, не меняет прототип врага и не оставляет постоянный дебафф для остальных игроков.
- Электрошок замедляет только движение. Повторное попадание обновляет срок, не складывает проценты; с другими замедлениями действует сильнейшее актуальное, без перемножения. На боссе величина равна **6,25%**, срок тот же; статичные черви не получают фиктивное замедление. Это отдельная сила эффекта, её нельзя выражать существующим таймером сильного замедления без величины. Оглушение, цепная молния и бесконечная блокировка атак не входят в свойство дубинки.
- Резак использует существующий тип `fire`, не новый тип «истинного урона». Он не создаёт дальнего снаряда, постоянного пожара или дополнительного горения сверх табличного удара. Одно добивание сохраняет обычный выход останков из раздела 2; последующее длительное выжигание тела подчиняется общей механике утраты сырья. Тело нельзя атаковать резаком повторно для добычи.

Ниже расчёт **без исследований, модулей и мутаций**, по одной постоянно доступной основной цели. DPS — теоретическая величина «урон / интервал», без подхода, промахов, замаха первого удара и переплаты уроном при добивании; это не время убийства. Средний ползун: **75 HP, F=4, pct=0,1**; панцирник: **900 HP, F=15, phys=0,55, elec=0,225, fire=−0,4** по правилам 1.15.

| Оружие | DPS до защиты основной цели | Урон по среднему ползуну / попаданий до гибели | Урон по панцирнику / DPS после защиты |
|---|---|---|---|
| Монтировка | **22,50** | **12,60 / 6** | **1,35 / 1,69** |
| Копьё | **32,00** | **25,20 / 3** | **7,65 / 7,65** |
| Тесак | **64,62** | **34,20 / 3** | **12,15 / 18,69** |
| Электрошоковая дубинка | **71,11** | **56,60 / 2** | **40,75 / 45,28** |
| Виброклинок | **153,85** | **93,48 / 1** | **68,15 / 104,85** |
| Плазменный резак | **127,27** | **133,00 / 1** | **196,00 / 178,18** |

Пример: против панцирника виброклинок даёт `(100 − 15×0,4) × (1 − 0,55×0,5) = 68,15`, резак — `140 × (1 − (−0,4)) = 196`. Дубинка — `max(1,12−15) × 0,45 + 52 × 0,775 = 40,75`. Поэтому термический резак выигрывает у этой конкретной брони, а виброклинок выгоднее для одиночных целей без огненной уязвимости; цена заряда и риск дистанции также различаются. Копьё и тесак сохраняют полезность там, где важнее дальность или отсутствие расходников.

**4. Управление, попадания и расход энергии**

- Оружие занимает существующий оружейный слот; выбранный вид определяет контактную атаку вместо выстрела. В UI показывать дальность/сектор, урон и типы, интервал, особенность, нужные заряды и текущий остаток. Контактный прототип имеет отдельные параметры `melee`, не маскируется винтовкой с отсутствующей категорией: старый код в таком случае подставляет `bullet`. Выбор и действие используют штатные назначения клавиш атаки/оружия; при удержании повтор начинается после полного интервала.
- В момент начала симуляция фиксирует направление и фазу замаха; в момент попадания проверяет актуальные координаты, живое состояние, дальность, сектор и препятствия. Удар по стене/закрытым воротам или через сплошную постройку не проходит к врагу за ней. Через дружественную цель нельзя наносить скрытый удар по врагу. Во время замаха скорость инженера умножается на **0,75** после обычных бонусов; во время восстановления возвращается обычная скорость. Поворот камеры не меняет зафиксированное направление.
- Допустимые цели — живые враждебные наземные существа, черви и гнёзда по действующей системе фракций. Летуны недоступны всем шести видам: для них остаётся дальнее оружие. Другие инженеры, дружественные биороботы, свои постройки, месторождения и трупы не получают урон от контактной атаки; демонтаж выполняется обычным инструментом. Удары по группе не проходят через препятствия к дополнительной цели.
- У каждого инженера общий остаток контактного заряда **0–20**; сначала **0**. Одна немодифицированная `laser-cell` из соответствующего слота боеприпасов или инвентаря даёт **20 единиц**, независимо от её обычного лазерного урона 22. На полностью оплаченный запуск дубинки/клинка/резака списываются **1/2/4** единицы; теоретически одна ячейка обеспечивает **20/10/5** ударов соответствующего вида. Размер/число попавших целей не увеличивает расход, промах его не возвращает.
- Если остатка мало, очередная ячейка загружается только в одной атомарной операции с оплатой удара; заряд не может превышать 20. Пример: осталось **2**, резаку нужны **4**, загружается ячейка 20, списываются недостающие 2 из неё — после оплаты остаётся **18**, старая двойка уже потрачена. Если целой ячейки нет, удар не начинается и старый остаток 2 сохраняется. Загрузка доступна только ради оплаты запуска, а не для накопления неограниченной энергии. Лазерная винтовка продолжает пользоваться своим прежним магазином; два счётчика не превращаются друг в друга.
- Смена/снятие оружия, вход в транспорт, копирование комплекта, сохранение и переподключение не пополняют контактный остаток. При гибели остаток теряется, возрождение начинается с 0; неиспользованные предметы ячеек подчиняются обычным правилам инвентаря/тела инженера. Зарядные модули брони не питают эту ветку автоматически. Для первого выпуска принимаются только ячейки без биопокрытия; существующий бонус боеприпаса не превращается в скрытый бонус контактного оружия.
- Есть один общий интервал атаки инженера, чтобы переключением слотов/дальнего оружия нельзя было сбросить восстановление. Смена оружия, смерть или вход в транспорт во время замаха отменяют ещё не нанесённый удар без возврата списанного заряда; исходный интервал сохраняется. Выход цели из сектора даёт промах. Повтор сетевой команды не создаёт вторую оплату/второй удар. В текущем creative-режиме используется согласованная политика расходников, но геометрия, фазы, сопротивления и интервал остаются теми же; возврат в выживание не генерирует заряд.

**5. Совместимость, сохранения и требования к реализации**

- Общий уже существующий бонус `damage` применяется один раз к каждому основному компоненту. Категорийные бонусы пуль/лазеров/огнемётов/Тесла и их скорости автоматически на контактное оружие не переносятся; отдельной бесконечной ветки усиления ближнего боя в этом предложении нет. Табличные интервалы фиксированы. Защитные модули и обычные щиты/броня инженера работают как прежде; биопокрытия для лезвий и дополнительные расходники не добавляются этой механикой.
- В формат **19** включить новые прототипы/исследования, контактный заряд каждого инженера, общий срок восстановления, зафиксированное направление, выбранное оружие и незавершённую фазу с тиком попадания. Если во время сохранения замах уже оплачен, загрузка не оплачивает его повторно; удар, ещё не завершённый на сохранённом тике, может завершиться один раз, прошедший удар не повторяется. Новая версия формата 20 не нужна. Миграция сохраняет прежние оружие/патроны/статистику, добавляет заряд 0 и доступные рецепты, не выдаёт готовые предметы/ячейки.
- В одиночке, браузерной партии до 8 игроков и на сервере до 16 симуляция проверяет владельца, выбранный слот, живое состояние, заряды и интервалы, сама выбирает цели и рассчитывает повреждения. Клиент передаёт направление/действие, а не список жертв или готовый урон. В момент гибели цель выдаёт один труп и один результат статистики, даже если по ней одновременно ударили разные игроки. Контактные фазы/заряд и новые эффекты замедления входят в состояние синхронизации/хеш; графика взмаха и звук остаются клиентскими.
- Общая пауза останавливает замах, восстановление и сроки эффектов. Закрытие окна экипировки не отменяет атаку. Выход игрока из партии отменяет не завершённый удар без возврата заряда, срок восстановления не сбрасывается; поздний вход получает актуальное состояние без повторной истории ударов. Для отмены при выходе и остальных переходах должен использоваться один авторитетный путь, чтобы переподключением нельзя было повторить попадание.

**6. Приёмка ветки ближнего боя**

1. В данных ровно **6** новых видов; каждый имеет свою роль, рецепт, этап открытия, сектор/дальность и параметры. Монтировка доступна без железной дороги, поздние рецепты/ячейки доступны через указанные технологии; миграция ранее изученных `military-2` и остальных исследований не требует повторения и не выдаёт предметы.
2. Расчёт таблицы воспроизводится по защите 1.15 без двойного применения сопротивлений; проверены панцирник, обычный враг, босс, мутация и дополнительные цели. Пробивание меняет только один удар; замедления не складываются, не оглушают и не превращаются в постоянную блокировку цели.
3. Для всех шести проверены интервалы/замах, направление, края сектора/дальности, отход цели, препятствия, предел 3 целей и отсутствие повторного попадания по одному id. Летуны, трупы и дружественные цели не получают контактный урон; гнёзда/черви получают его по своим корректным боевым правилам.
4. Ячейка даёт ровно 20 единиц, цены 1/2/4 дают 20/10/5 запусков. Пройдены остаток 2 + новая ячейка → резак → 18, нехватка зарядов без потери остатка, промах/отмена, смена оружия, общий интервал с выстрелом, гибель/возрождение и переход creative → survival. Биоизделие или старый лазерный магазин не становится бесплатным зарядом.
5. Сохранение/загрузка в ожидании, замахе и восстановлении, пауза, переподключение, повтор команды и конкурирующее добивание не дублируют расход, урон, трупы или статистику. Проверены одиночка, браузерная партия и сервер до 16; авторитетные состояния/полные хеши совпадают.
6. В боевых прогонах измерены фактическое время убийства, полученный инженером урон, расходы и массовая эффективность всех шести против малого/среднего/большого ползуна, плевуна, панцирника, разрушителя и босса. Подтверждены полезность копья по дистанции, тесака без расходников, дубинки для отхода, виброклинка в дуэли и резака по огненной уязвимости/группе; при доминировании одного вида баланс пересматривается.
7. Проверены прежние пистолет/винтовки, турели, щиты/модули, фракции биороботов, выход биопроб и творческий режим; нагрузочный прогон с 16 атакующими инженерами не создаёт неограниченный перебор всех целей каждый тик. Это будущая приёмка реализации; текущая правка создаёт концепцию и расчёт, а не работающие виды оружия.

**Передача:** сначала монтировка с одним ударом, общим интервалом и сохранением фазы → копьё/тесак и геометрия → заряд/дубинка и слабое замедление → виброклинок/резак и проверка сопротивлений → мультиплеер и боевой баланс. Числа утверждаются после прототипа; новые реальные научные свойства оружия из этого описания не выводятся.

#### 6. Боевые дронопорты и шесть видов боевых дронов

**Замысел:** специальный дронопорт выпускает настоящие обслуживаемые машины для поддержки оборонительной линии. Инженер может установить отдельный личный боевой дронопорт в броню и брать небольшой отряд с собой. Шесть ролей: стрелковая поддержка, перехват летунов, ракетная атака по группе, электрическое сдерживание, термическая атака по панцирю и ремонт под огнём. Одна модель не заменяет все роли; боеприпасы, электричество, ремонт и потери оплачиваются фабрикой.

**Исходная база:** в 1.15 уже есть строительные/логистические роботы, робопорты и модуль `combat-drone-equipment`: **2×2**, **150 кВт**, три условных дрона с лазерными попаданиями из `stepKit`. Это эффект оборудования, а не три отдельных машины с HP, батареей, боекомплектом и жизненным циклом. Его рецепт/технология/поведение сохраняются как прежнее снаряжение. Ниже вводятся отдельные новые предметы и состояния; строительный личный робопорт не становится боевым автоматически. Размеры, числа и цены — стартовые предложения для прототипа.

**3. Энергия, ремонт и жизненный цикл**

- Состояния: стоянка → зарядка/снабжение → резерв и вылет → бой/ремонт → возврат → стыковка/обслуживание; отдельно вынужденная посадка, отключение связи и гибель. Батарея хранит фактические МДж; зарядка не превышает мощность источника и свободную ёмкость, **1 МДж = 1 000 кДж**. Недостаток питания уменьшает зарядку, а не создаёт энергию. Боевые дроны после вылета работают от батареи, поэтому потеря питания порта не гасит их мгновенно.
- Вылет требует не менее **80%** батареи, доступного задания/связи и достаточного ресурса для возвращения. Возврат начинается при остатке ниже максимума из **20% ёмкости** и расчётной энергии пути к посадочному месту с запасом, при исчерпании боекомплекта/ремонтного бюджета либо команде возврата. При возврате новые атаки не расходуют резерв. Неуспешная оплата полного импульса не создаёт частичный бесплатный удар.
- Снаряжение передаётся между реальными буферами атомарно; магазин открывается на его действительное число зарядов, выстрел списывает заряд, ракета/импульс топлива списываются один раз. Стыковка не выдаёт новую полную канистру/магазин вместо остатка. Возврат и ремонт дрона в порту тоже расходуют наборы по бюджету **200 HP/набор**; создание, перемещение, снятие личного модуля и повторное подключение не лечат повреждённую машину бесплатно.
- Дрон существует либо как экземпляр предмета на стоянке/в инвентаре, либо как единица в мире. Его стабильный id, тип, HP, батарея, боекомплект и частичный ремонтный бюджет сохраняются при переносе; это предмет с размером стека **1** и состоянием, обычное объединение/сортировка не должны превращать его в новый полный предмет. Резерв вылета/стыковка переводят одно представление в другое, никогда не создают две копии. Клиент не присылает произвольные HP/заряды для импортируемого экземпляра.
- Штатное снятие личного модуля/демонтаж порта сначала переводит находящиеся на стоянке экземпляры и расходники в доступный инвентарь по обычным правилам, сохраняя состояние; при нехватке места операция ждёт освобождения/выгрузки, не уничтожает содержимое. Летающим машинам выдаётся возврат/посадка по правилу потери источника. Уничтожение порта в бою применяет обычную потерю его хранимого содержимого один раз; оно не превращает стоянковые машины в новый бесплатный отряд.
- Если источник исчез/перемещён или личный инженер умер/вышел из партии, дрон прекращает новые задания и пытается вернуться к доступному совместимому порту с правами владельца и местом в зоне своей связи. Если такого места нет — контролируемая посадка/неактивная машина в фактической точке; её можно забрать как тот же экземпляр. Пустая батарея не телепортирует машину в инвентарь. При повторном входе старые машины восстанавливаются по id, новый бесплатный отряд не создаётся.
- Открытая/закрытая панель не меняет задания. Пауза мира останавливает таймеры/потребление, серверный `pauseWhenEmpty` имеет то же правило. Стационарная оборона при работающем сервере действует без игрока; личный отряд следует правилам отсутствующего владельца. При транспортировке инженера личный отряд возвращается/следует в пределах допустимой связи и резерва, не дублируется сменой карты/транспорта.

#### 7. Доступные ячейки во всех сундуках

**Замысел:** игрок может оставить сундуку все ячейки либо только **1, 2, 3, 4** и любое другое количество до его физической вместимости. Это ограничивает приём/накопление предметов, помогает дозировать производство и сохраняет уже находящиеся внутри вещи.

**Исходная база:** `Inventory` в 1.15 хранит массив фиксированной вместимости; поиск свободного места и добавление перебирают все слоты, сохранение содержит весь массив. Отдельного лимита доступных ячеек в этих путях нет. В данных: деревянный сундук **16**, железный **32**, стальной/пять логистических **48**, обычный и пять логистических складов **300**. Новое правило применяется ко всем постройкам `type: 'chest'`, включая эти **14** прототипов и совместимые модовые сундуки; другие буферы машин/вагоны/инвентарь инженера этим переключателем не ограничиваются.

**1. Управление и понятный результат**

- В окне сундука добавить **«Доступные ячейки: [Все ▾]»**. В списке быстрые варианты **«Все», «1», «2», «3», «4»** с доступностью только при N≤S, затем **«Другое…»** с вводом/ползунком **1…S**, где S — физическая вместимость. По умолчанию «Все»; исследования и расход предметов не нужны. Значение 0 не вводится неявно как обозначение всех/ошибка ввода.
- При N открыты первые N ячеек по стабильному порядку слева направо/сверху вниз; остальные затемнены и отмечены замком. Полная сетка остаётся видна. Над ней статус «Открыто N из S»; если в закрытых местах уже есть вещи — «Вне лимита: K занятых ячеек». Из них разрешено забрать предметы, но положить новые нельзя.
- Менять лимит можно в существующем сундуке, в том числе непустом. Уменьшение не удаляет/не перемещает вещи автоматически и не обрезает массив. Увеличение/«Все» снова разрешает приём в открытых местах; количество предметов от этого не меняется. Ограничивается число слотов, а не число единиц предмета: одна ячейка железных пластин по данным 1.15 хранит до **100**.

**2. Единые правила всех путей передачи**

- Новый приём и дозаполнение стека разрешены только внутри открытого диапазона и с действующими фильтрами. Это правило общее для ручного помещения, быстрого переноса, манипулятора, логистической доставки и внутренних команд перемещения. В уже занятую закрытую ячейку нельзя незаметно дописывать новые единицы того же предмета. Взятие/вывоз из любой занятой ячейки разрешены, включая закрытые.
- `space/add` и проверка приёмника используют одно значение лимита; `size`/полный массив остаются S. `count/items`, сигналы схемотехники и снабжение по остатку считают **всё фактическое содержимое**, включая превышение лимита. Контейнер не становится пустым из-за закрытия слота. «Все» хранится как отдельное состояние, а не магическое N=0.
- Логистические запросы и резервирование доставки учитывают свободные разрешённые ячейки/фильтры и уже запланированный груз. Если N уменьшили после вылета робота, при прибытии повторно проверяется реальная ёмкость: лишнее не теряется и не кладётся в закрытые места, доставка ждёт/переназначается по штатным правилам. Манипулятор с предметом в руке удерживает его при отсутствии допустимого места. Частичная передача возвращает/сохраняет непоместившийся остаток.
- Сортировка упорядочивает только открытый диапазон; закрытые занятые ячейки сохраняют содержимое до извлечения. Она не отбрасывает переполнение и не объединяет уникальный повреждённый/заряженный дрон в полный предмет. Фильтр ячейки сохраняется после закрытия и снова действует при открытии. Лимит и фильтры совместно определяют допустимый приём.
- Копирование настроек/чертежи/призраки сохраняют выбранный лимит без предметов. «Все» при копировании на другую вместимость остаётся «Все», числовой N ограничивается новой S; повышение/замена сундука переносит содержимое/фильтры и применяет тот же смысл лимита. Понижение вместимости не уничтожает переполненный груз: используются существующие правила допустимой замены/возврата остатка.

**Проверочный пример:** в первой ячейке **60** железных пластин, лимит **1**. Из входящих **70** принимаются **40**, остаются **30** у отправителя; закрытый слот не заполняется. Если в другой закрытой ячейке уже лежало 20 пластин, там остаются 20, общее содержимое после операции **120**, свободное место для нового приёма **0**. Открытие «Все» меняет доступную ёмкость, а не количество 120.

**3. Сохранения и приёмка**

Лимит — состояние постройки в формате **19**, входит в команды/снимки/хеши. Авторитет проверяет право взаимодействия и целое N в 1…S либо явное «Все»; дробь, NaN, отрицательное и значение больше S из сетевой команды отклоняются. Старые сундуки мигрируют в «Все» с прежним содержимым. Настройка не позволяет гостю обходить доступ к чужой постройке; UI не является единственным местом ограничения.

1. Все **14** базовых прототипов и совместимый модовый сундук поддерживают «Все / 1 / 2 / 3 / 4 / другое»; фактическая физическая вместимость остаётся 16/32/48/300. Первые N мест, фильтры и понятный статус соответствуют выбору.
2. Уменьшение/увеличение, занятые закрытые места, дозаполнение, частичный перенос и пример 60+40/остаток 30/общие 120 сохраняют предметы. Ручной приём, манипулятор и робот не обходят лимит; извлечение и сигналы считают весь запас.
3. Запрос/доставка при изменении N в пути, занятый фильтр и предмет в руке не теряют/не дублируют груз. Сортировка, копирование/чертёж и замена вместимости не обрезают массив, не удаляют уникальные экземпляры и сохраняют смысл «Все».
4. Одиночка/браузерный кооператив/сервер проходят save/load, поздний вход, повтор команды, конкурирующие изменения и проверку недопустимого N; совпадают содержимое/лимит/хеши.
5. Старые фабрики после миграции принимают предметы с прежней вместимостью; обычные инвентари/вагоны/буферы и пять логистических ролей сундуков проходят регресс. Это требования к будущей реализации переключателя, а не уже доступная кнопка.

#### 8. Исправление: после насыпи визуально остаётся вода

**Сообщение игрока:** насыпь ставится, но вода продолжает отображаться. **Приоритет — обязательное исправление перед выпуском 1.17.0**, может быть доставлено раньше отдельным исправлением после проверки соответствующей сборки. Регистрация проблемы в этом ТЗ не означает её исправления в игровом архиве.

**Наблюдение по исходникам 1.15:** `Game.fillLand` меняет `c.terrain[i]` на сушу, записывает индекс в `c.land`, увеличивает `c.version` и `landVer`; клиентское зеркало принимает изменённый terrain/version. `buildGeo` сохраняет версию, но `Renderer.geoFor` возвращает уже имеющуюся геометрию по ключу чанка без проверки её версии. Сброс соседей сейчас показан для генерации нового чанка. **Вероятная причина по чтению кода** — после насыпи остаётся старая геометрия водной поверхности/берега; это надо подтвердить воспроизведением в поставляемой сборке, поскольку визуальный прогон здесь не выполнен.

**Требуемый результат и путь исправления**

- После авторитетного размещения новая суша отображается на следующем кадре после получения обновления: водная заливка/волны не остаются поверх засыпанного участка, берег/пена перестраиваются. Поверхность, проходимость, возможность строительства и карта используют один результат изменения terrain; насыпь не является лишь визуальной наклейкой поверх логической воды.
- Связать изменение рельефа с инвалидированием геометрии и производных изображений затронутого чанка и соседей, участвующих в построении берега. Включить canvas/webgl/legacy, LOD/миникарту и клиентское зеркало. Для края/угла чанка проверить нужную соседнюю область, стартово до **3×3 чанков**; окончательный охват определяется чтением зависимости сглаживания. Обычная добыча руды/движение существа не должны постоянно пересобирать весь водный рельеф.
- Рассмотреть отдельную ревизию рельефа либо явное событие изменения terrain; одной проверки общей `c.version` может не хватить для соседних берегов и она может быть слишком дорогой при изменениях руды/занятости. Конкретный минимальный механизм выбрать после воспроизведения и замера. Не исправлять проблему перезагрузкой страницы, сменой seed или очисткой всей карты каждый кадр.
- Сохранённый `c.land` уже содержит результат насыпи; загрузка/миграция не списывает ещё предмет и не превращает сушу обратно в воду. Одновременное размещение двумя инженерами на одной клетке изменяет её один раз, повтор команды не дублирует оплату. Исправление сохраняет обычную кисть, бетон/снятие покрытий и генерацию незатронутой воды.

**Приёмка исправления**

1. Воспроизвести проблему и записать сборку/режим отрисовки/координаты/размер кисти: мелкая и глубокая вода, уже закэшированный участок, центр/край/угол чанка. После изменения новая суша и берега видны без перезагрузки; карта/LOD и все поддерживаемые режимы согласованы.
2. Проверены одиночка, два клиента кооператива и выделенный сервер: размещение на клиенте, повтор/одновременная команда и поздний вход одинаково обновляют terrain и изображение, нет двойного расхода насыпи; хеши мира совпадают.
3. Save/load, уход/возврат камеры, генерация соседнего чанка, другой масштаб и продолжение старого сохранения не возвращают воду. По новой суше можно пройти/поставить допустимую постройку, оставшаяся вода остаётся водой; бетон/демонтаж не возвращают бесплатно насыпь.
4. Большая кисть/серия заполнений обновляют ограниченную область, измерены число пересборок и кадры; нет полной пересборки карты из-за добычи руды/дронов. К выпуску требуются наблюдаемый визуальный результат и регресс, одной правки текста/чтения кода недостаточно.

#### 9. Расширение инвентаря: 32 ячейки на старте, семь технологий до 256

**Назначение.** Вместимость основного инвентаря инженера растёт вместе с развитием фабрики. В новом мире инженер начинает с **32 ячеек**; доступны ровно **семь последовательных улучшений по +32 ячейки**. Итоговая цепочка: **32 → 64 → 96 → 128 → 160 → 192 → 224 → 256**. Это число мест под стопки, а не число отдельных предметов и не размер стопки. Предельная обычная вместимость — **256**, бесконечной восьмой технологии нет.

**Подтверждённая база 1.15.** В `src/sim/game.ts` основной инвентарь и инвентарь нового участника создаются через `new Inventory(80, true)`; `src/sim/save.ts` также создаёт инвентарь загружаемого участника на 80 мест. `Inventory.load` копирует только до своей `size`, поэтому простая замена 80 на 32 при загрузке может потерять содержимое хвоста. | V — `inventory-expansion-5` | **192** | IV + `advanced-electronics-2` | Красный, зелёный, синий | 450 / 30 |
| VI — `inventory-expansion-6` | **224** | V + `production-science-pack` | Красный, зелёный, синий, фиолетовый | 600 / 30 |
| VII — `inventory-expansion-7` | **256** | VI + `utility-science-pack` | Красный, зелёный, синий, фиолетовый, жёлтый | 800 / 45 |

Красный/зелёный/синий/фиолетовый/жёлтый соответствуют существующим `automation-science-pack` / `logistic-science-pack` / `chemical-science-pack` / `production-science-pack` / `utility-science-pack`. Космическая наука для достижения 256 не требуется. Карточка каждой ступени показывает «+32 ячейки: 128 → 160», зависимости и полную стоимость; VII сообщает «Максимум: 256». Это развитие переносимого комплекта инструмента/снаряжения, без нового расходуемого предмета, бонуса брони или изменения скорости инженера.

**Правила применения и сохранность предметов**

- Исследования общие для фабрики, как остальная ветка технологий. Завершение ступени расширяет основной инвентарь **каждого** инженера: хозяина, подключённых участников, сохранённых отключённых участников. Новый участник и возрождённый инженер получают вместимость текущего мира; им не выдаётся начальная версия на 32 или прежние 80 вопреки уже завершённой ветке. Стартовые предметы и правила смерти/возрождения сохраняют свою прежнюю логику.
- Один расчёт вместимости: `slots = 32 + 32 × L`, где `L` — уровень завершённой последовательной ветки от 0 до 7. Каждый ID учитывается один раз; повтор сообщения о завершении исследования не добавляет ещё 32. Новое поле эффекта технологии, если оно вводится, и вычисление по ID не должны одновременно начислять один и тот же бонус. Обычный игрок не может командой клиента повысить L, исследовать заблокированную ступень или превысить 256.
- Расширение выполняется авторитетной симуляцией на тике завершения исследования. Дописываются 32 пустые ячейки, меняется `size`; существующие стопки, их индексы, фильтры, предмет в руке, экипировка и очереди действий сохраняются. Расширение само по себе не сортирует/не объединяет предметы. Для уникальных экземпляров боевых дронов сохраняются ID, заряд, здоровье и остальные данные, а не только название/количество.
- Сундуки и их новый предел приёма раздела 7, склады, вагоны, входные/выходные буферы машин, слоты оружия и сетка брони не получают +32. Панель быстрого доступа остаётся набором ссылок на предметы; она не создаёт отдельный запас и не занимает дополнительные физические ячейки.
- Все способы получения/переноса предметов используют актуальную вместимость: ручной перенос, крафт, добыча, демонтаж, быстрый перенос, логистическая доставка, обмен и возврат предмета из руки. Старые ограничения на 80 в этих путях, UI, клиентском зеркале и сериализации подлежат замене единым расчётом. Обновление вместимости и перенос на том же тике имеют определённый порядок; остаток возвращается по прежнему безопасному правилу, без исчезновения или удвоения груза.
- При `/creative` → `/survival` вместимость восстанавливаемого инвентаря соответствует текущим технологиям мира. Сохранённый на время креатива инвентарь расширяется вместе с веткой и возвращает прежние предметы; переключение режима не сбрасывает исследования, не начисляет семь ступеней и не обрезает хвост. Сохраняются права на команды и `cheatsUsed` из ТЗ 1.16. В рамках этого пункта отдельная команда уменьшения вместимости не вводится.

**Интерфейс**

В окне инвентаря: «Занято: 21 / 64 ячейки · улучшение I / VII». Рядом доступен переход к следующему исследованию; на максимуме — «256 · максимум». Новые места сразу отображаются и доступны для переноса. Сетка адаптируется к ширине окна, прокручивается внутри панели и остаётся доступной на небольшом экране при 256 местах; поиск/подсветка и горячие клавиши работают для последней ячейки. Уведомление о завершении: «Инвентарь расширен: 64 → 96 (+32)», одно на ступень для подключённого игрока, без повторения всей истории при позднем входе.

**Сохранение, сеть и миграция в общий формат 1.17**

- Завершённые ID ветки входят в общий `research.done`; основной массив каждого участника и сохранённый для возврата из креатива массив имеют нужную длину. До `load`/переноса данных сначала определяется вместимость и создаётся подходящий `Inventory`, затем копируются все предметы. Одного изменения массива на клиенте недостаточно: `size`, массив, зеркало и серверный снимок должны быть согласованы.
- Вместимость 256 нельзя кодировать однобайтовым беззнаковым числом. Допустимые индексы — **0…255**, индекс 255 является обычной доступной ячейкой; 256, отрицательные, дробные и нечисловые индексы отклоняются. Поля ёмкости/пакеты сети/проверки команд не должны превращать 256 в 0 или использовать последний действительный индекс как признак «нет ячейки».
- Для старого поддерживаемого мира 1.15/1.16 с обычными 80 местами провести **однократную миграцию 80 → 96**: отметить I–II завершёнными для всей фабрики, дописать 16 пустых мест и сохранить все прежние вещи. Это совместимость, а не платное исследование: наука повторно не списывается. Другие технологии из зависимостей таблицы автоматически не открываются. Дальнейшая ступень III имеет свои обычные зависимости и цену.
- При импорте совместимого сохранения с другой прежней вместимостью до 256 выбрать минимальную ступень, которая вмещает **максимальную сохранённую ёмкость всех основных/отложенных инвентарей участников**, учитывая также уже завершённую ветку. Массив не обрезается по числу занятых мест; предмет в последней позиции не теряется. Миграция и выдача исследованных эффектов выполняются один раз, повторное сохранение/вход не начисляют следующую ступень. Если данные не укладываются в поддерживаемые 256 или повреждены, импорт останавливается с понятной ошибкой и сохраняет исходный файл; молча обрезать данные нельзя.
- Отключённые игроки, поздний вход, переход браузерного мира на сервер, перезапуск и восстановление снимка сохраняют одну общую ветку и содержимое всех инвентарей. Используется уже предусмотренный формат **19**, без отдельной несовместимой версии ради одной вместимости. Увеличенный инвентарь входит в хеши состояния; полномочия и проверки количества/слотов выполняются на стороне авторитета.

**Приёмка расширения инвентаря**

1. Новый мир во всех трёх режимах начинает с 32 мест; последовательное исследование семи ступеней даёт ровно 64/96/128/160/192/224/256. Пропуск зависимостей и восьмое улучшение недоступны; не меняются размеры стопок и других контейнеров.
2. Заполненный инвентарь, предмет в руке, экипировка, очередь крафта, фильтры и уникальный дрон переживают каждое расширение без потерь/пересортировки/дубликатов. Перенос/доставка на тике исследования корректно используют новую ёмкость.
3. Все участники, включая отключённого/нового/возрождённого, получают общий эффект. Поздний вход, save/load, перезапуск и перенос мира на ПК-сервер сохраняют данные; повтор события не расширяет инвентарь дважды, хеши совпадают.
4. Старый мир с 80 местами и предметом в ячейке 79 мигрирует в 96 с I–II, без оплаты и лишних разблокировок; повторная загрузка остаётся на 96. Импорт другой поддерживаемой ёмкости сохраняет хвост всех участников; неподдерживаемые данные отклоняются без перезаписи оригинала.
5. После расширения во время креатива возврат в выживание восстанавливает запас и текущую ёмкость, сохраняет `cheatsUsed`. Индекс 255 принимается при 256 местах, 256/некорректные индексы отклоняются авторитетом; UI на небольшом экране даёт доступ ко всем местам. Это приёмка будущей реализации, не утверждение о готовом изменении архива.

#### 10. Автоматическая цепочка электростолбов при удержании мыши

**Поведение для игрока.** Выбрать электростолб, поставить первый нажатием ЛКМ и, не отпуская кнопку, вести курсор в нужном направлении. Следующие столбы автоматически ставятся **с максимально возможным шагом, при котором соседние столбы соединяются электрическим проводом**. Одиночный щелчок сохраняет обычное точное размещение; специальный модификатор и отдельная технология для новой укладки не требуются.

**Подтверждённая база 1.15.** `src/main.ts::onDragTo` сейчас использует для обычных построек шаг `max(w, h)`; это не максимальная длина электрического провода. `src/sim/networks.ts::rebuildPower` связывает пары по расстоянию между центрами, не превышающему `min(wireA, wireB)`. Для этой электрической сети в данном коде не задан предел «пять соединений на столб». Провод схемотехники и его дальность не определяют новый шаг электростолбов.

| Прототип | Размер | Электрический провод между одинаковыми опорами | Максимальный прямой шаг по горизонтали/вертикали на целой сетке |
|---|---:|---:|---:|
| Малый столб — `small-electric-pole` | 1×1 | **7,5** клетки | **7** клеток |
| Средний столб — `medium-electric-pole` | 1×1 | **9** клеток | **9** клеток |
| Большая опора — `big-electric-pole` | 2×2 | **30** клеток | **30** клеток |
| Подстанция — `substation` | 2×2 | **18** клеток | **18** клеток |

Новая укладка применяется ко всем четырём электрическим прототипам. Для совместимого модового `type: pole` шаг берётся из его действительного `wire`, а размер — из прототипа. Не заменять таблицу жёстким шагом 7/9/30/18 в обработчике мыши.

**Контракт построения**

- Первая успешно поставленная опора становится якорем цепочки. Неуспешный щелчок по воде/занятой клетке не создаёт якорь и не списывает предмет. Начать от уже существующей совместимой опоры можно щелчком по ней с выбранным электростолбом; используется её фактический центр и прототип, новая копия поверх неё не ставится.
- Расстояние считается как `sqrt((cxA − cxB)² + (cyA − cyB)²) ≤ min(wireA, wireB)` с теми же численными правилами, что у `rebuildPower`. Центры учитывают размеры обоих объектов. Для одинаковых 1×1/2×2 на прямой выполняется таблица; при переходе между малой и большой опорой допустимое расстояние — 7,5 между центрами, а не 30 и не расстояние между левыми верхними клетками.
- Для текущего направления показать следующую допустимую позицию на сетке у границы дальности провода. Зафиксировать способ дискретизации линии и разрешение равных кандидатов; симуляция/предпросмотр используют один алгоритм. Из допустимых позиций на задаваемом участке выбирается самая дальняя, сохраняющая связь с якорем. Не округлять дальность вверх и не подменять евклидово расстояние суммой координат: диагональный сдвиг малого столба `(5, 5)` допустим, `(6, 6)` — нет.
- Пока курсор не дошёл до следующей максимальной позиции, нового столба нет. При достижении/прохождении позиции разместить его, продвинуть якорь и повторить для оставшегося участка. Быстрое движение или редкие события мыши не оставляют разрыв: между далёкими положениями курсора достраиваются все промежуточные шаги. Остановка курсора не создаёт столбы по таймеру; число кадров/повторов `mousemove` не задаёт шаг. Поворот направления продолжает цепочку от последней подтверждённой опоры и не перестраивает уже проложенную часть.
- Если максимальная точка занята/непригодна, можно выбрать наиболее далёкую доступную точку на том же участке в пределах провода; UI показывает укороченный шаг и причину. Нельзя перепрыгнуть непроходимую область дальше допустимой связи. Когда допустимой точки с продвижением нет, остановить участок и показать препятствие; обход выбирает игрок. Уже подходящая опора по пути может стать следующим якорем без расхода предмета. Область питания предприятий не является критерием такой замены.
- Каждый реальный столб проходит обычные проверки строительства, доступа/дистанции инженера, занятости клеток и наличия предметов. За него списывается ровно одна соответствующая опора по правилам текущего режима. Якорь продвигается только после подтверждения размещения или принятия существующего объекта; при отказе нельзя продолжать длинную цепь от несуществующего столба. Без предметов/при выходе из дистанции участок останавливается с понятным статусом.
- В предусмотренном режиме призраков тот же расчёт создаёт цепочку призраков и показывает будущие связи, не расходуя опоры заранее. Такая цепочка не питает машины до строительства реальных столбов; планируемые связи визуально отличаются от действующих. Обычный жест не переключается самовольно на призраки при исчерпании запаса.
- Отпускание ЛКМ прекращает укладку; неполный остаток до курсора **не заполняется укороченным последним столбом автоматически**. Для короткого окончания можно сделать отдельный щелчок. Escape, смена предмета/инструмента, открытие меню, потеря фокуса/захвата кнопки и отключение клиента также завершают жест. После загрузки/повторного входа удержание не восстанавливается и не строит само.

**Обратная связь**

Предпросмотр выделяет якорь, следующий столб, соединяющий провод и зоны питания обоих столбов. При выходе за дальность/препятствии причина читается рядом с курсором; при смешанных типах показан ограничивающий шаг. Максимальный шаг провода **не гарантирует сплошного покрытия машин электричеством**: радиус питания малого столба 2, среднего 3, большой опоры 1 и подстанции 8 остаётся прежним. Игрок видит промежутки покрытия и может заполнить их отдельными щелчками. Размещение электрической цепочки не протягивает красный/зелёный провод автоматически.

**Авторитет, сеть и производительность**

Обработчик удержания формирует строительные намерения; обычный авторитет выполняет оплату/размещение и проверяет связь последовательных шагов. Для длинного участка разрешены ограниченные пакеты с последовательностью команд/ссылкой на предыдущий якорь; очереди должны учитывать уже зарезервированные опоры и доступную дистанцию. Сервер не доверяет заявлению клиента «здесь связь допустима». Дубликаты/повтор доставки не списывают второй предмет; если якорь удалён или точку занял другой игрок, участок отклоняется/пересчитывается от последнего действительного якоря, без прыжка через отказ. Локальная отмена сразу прекращает генерацию намерений; принятие отмены авторитетом снимает ещё не исполненную часть очереди этого жеста. Уже исполненные столбы остаются в мире; порядок пакетов/отмены определён и не зависит от перестановки сетевой доставки. Частота пакетов не зависит от FPS, число кандидатов/команд на обработку ограничивается; для далёкого курсора не выполняется полный поиск всех столбов карты.

Сохраняются сами опоры и обычная электрическая сеть, а не состояние зажатой кнопки. Поздний вход и перезапуск получают те же построенные объекты/связи. Для локальной симуляции, Worker и кооператива требуется единый результат по одному и тому же пути намерений; предпросмотр обновляется по подтверждениям. Ленты, трубы, рельсовый планировщик и прочие инструменты продолжают использовать свои правила укладки.

**Приёмка автоматической расстановки**

1. На свободном прямом участке при достаточном запасе и доступности позиций инженеру малые столбы от `(0, 0)` до курсора `(23, 0)` располагаются в `(0, 0)`, `(7, 0)`, `(14, 0)`, `(21, 0)`; отпускание не ставит дополнительный в 23. Средние/большие/подстанции идут с шагом 9/30/18; соседние опоры входят в одну электрическую сеть.
2. Проверены горизонталь, вертикаль, диагональ, поворот, отрицательные координаты, 2×2 и смешанная пара. Малые `(5, 5)` соединяются, `(6, 6)` не принимаются как соседний шаг; в смешанной цепи используется меньшая длина и реальные центры. Отдельный щелчок ставит опору на допустимом коротком расстоянии.
3. Вода/чужая постройка/встречная опора/удалённый якорь/конец запаса/граница доступа дают описанный результат без разрыва, дубля и лишнего расхода. Призраки сохраняют шаг, но не создают питание; отображение зон питания честно показывает возможные промежутки.
4. Один длинный перенос курсора и множество промежуточных событий по той же прямой, при разных FPS, дают одинаковую цепь. Mouseup/Escape/смена инструмента/меню/потеря фокуса прекращают дальнейшие намерения; повтор команды и конфликт двух строителей сохраняют предметы.
5. Одиночка, Worker, браузерный кооператив и сервер проходят построение/отмену/поздний вход/save/load/перезапуск с одинаковыми объектами, проводами и хешами. Проверена ограниченная очередь длинного участка и регресс укладки других построек. Это новое поведение для реализации, а не уже включённая функция сборки 1.15.

#### 11. НПЗ и химзавод: видимые жидкостные входы/выходы выбранного рецепта

**Проблема и результат.** По зданию должно быть сразу понятно, **какую жидкость к какому штуцеру подключить и где забрать продукт**. На НПЗ и химическом заводе показывать реальные физические точки подключения, направление «вход/выход», значок и название требуемой рецептом жидкости. Поворот здания, смена рецепта и наличие трубы не должны делать метку неверной или скрывать её под спрайтом.

**Подтверждённая база 1.15.** В `src/data/entities.ts` НПЗ 5×5 имеет два входных бака/три выходных, химзавод 3×3 — два входных/два выходных. В `Game.setFluidFilters` жидкие элементы `recipe.in` и `recipe.out` выбираются **в порядке массива рецепта**, затем назначаются последовательно входным/выходным бакам прототипа; твёрдые ингредиенты пропускаются. `fluidConns` переводит локальные штуцеры в мировые координаты и поворачивает направление. Визуализация должна отображать именно это действительное назначение, без отдельного списка «красивых» выходов.

**Точная схема подключения при исходном повороте `dir = 0`**

Координаты — клетки внутри неповернутого здания, от левого верхнего угла, x вправо/y вниз. «Снизу/сверху» — сторона подключения внешней трубы; стрелка входа направлена **внутрь** здания, выхода — **наружу**. I/O — устойчивые имена точек для описания и отладки, в обычной подсказке используется понятное «Вход: вода».

| Здание | Точка | Локальная клетка штуцера | Внешняя труба при `dir = 0` |
|---|---|---|---|
| НПЗ 5×5 | I1 / вход 1 | `(1, 4)` | `(1, 5)`, снизу |
| НПЗ 5×5 | I2 / вход 2 | `(3, 4)` | `(3, 5)`, снизу |
| НПЗ 5×5 | O1 / выход 1 | `(0, 0)` | `(0, −1)`, сверху слева |
| НПЗ 5×5 | O2 / выход 2 | `(2, 0)` | `(2, −1)`, сверху по центру |
| НПЗ 5×5 | O3 / выход 3 | `(4, 0)` | `(4, −1)`, сверху справа |
| Химзавод 3×3 | I1 / вход 1 | `(0, 2)` | `(0, 3)`, снизу слева |
| Химзавод 3×3 | I2 / вход 2 | `(2, 2)` | `(2, 3)`, снизу справа |
| Химзавод 3×3 | O1 / выход 1 | `(0, 0)` | `(0, −1)`, сверху слева |
| Химзавод 3×3 | O2 / выход 2 | `(2, 0)` | `(2, −1)`, сверху справа |

| Здание / рецепт из 1.15 | I1 | I2 | O1 | O2 | O3 |
|---|---|---|---|---|---|
| НПЗ: `basic-oil-processing` — простая переработка | Сырая нефть | Не используется | Нефтяной газ | Не используется | Не используется |
| НПЗ: `advanced-oil-processing` — глубокая переработка | Сырая нефть | Вода | Тяжёлая нефть | Лёгкая нефть | Нефтяной газ |
| Химзавод: `plastic-bar` — пластик | Нефтяной газ | Не используется | Не используется | Не используется | — |
| Химзавод: `sulfur` — сера | Нефтяной газ | Вода | Не используется | Не используется | — |
| Химзавод: `sulfuric-acid` — серная кислота | Вода | Не используется | Серная кислота | Не используется | — |
| Химзавод: `heavy-oil-cracking` — крекинг тяжёлой нефти | Тяжёлая нефть | Вода | Лёгкая нефть | Не используется | — |

**Пример, который нельзя перепутать:** в простой переработке газ выходит через **O1 слева**, а при глубокой — через **O3 справа**. Не закреплять иконку газа навсегда справа. Уголь для пластика, сера/железо для кислоты и твёрдые продукты не становятся жидкостными штуцерами; манипуляторы для них описываются отдельно в рецепте.

**Отображение и взаимодействие**

- У каждого используемого штуцера — небольшая контрастная рамка/плашка, иконка жидкости и стрелка направления потока. Вход и выход различаются стрелкой и подписью, а цвет жидкости служит дополнительной подсказкой. Стрелка не показывает текущее течение внутри общей сети и не зависит от количества жидкости; это назначение подключения по рецепту.
- Метки обязательно видны при наведении/выделении здания, размещении здания с заданным рецептом, размещении подходящей трубы рядом и в режиме Alt. В обычном обзоре без этих условий можно оставить компактные обозначения точек; плотный завод не закрывается постоянными длинными подписями. Настройка видимости не меняет физические подключения. При подключённой трубе значок остаётся читаемым и не перекрывает взаимодействие с трубой.
- При наведении на метку/штуцер: «Вход: вода · требуется 50 ед. на цикл» либо «Выход: нефтяной газ · 55 ед. на цикл» для глубокого НПЗ. Количество берётся из **текущего** рецепта; это базовый расход/выход за цикл, не обещание производительности в секунду и не фактическая выдача с продуктивностью. Дополнительно можно показать «Сеть: вода, … ед.»/«Нет подключения»/«Другая жидкость в сети» по существующим данным без подмены назначения порта фактическим содержимым сети.
- Неиспользуемый рецептом штуцер отмечается приглушённым знаком и подсказкой «Не используется в этом рецепте»; ему не приписывается оставшаяся жидкость прошлого рецепта. Если рецепт ещё не выбран, показать контур входных/выходных точек и «Выберите рецепт», без иконки нефти/воды по умолчанию.
- Смена рецепта обновляет все назначения вместе с авторитетным состоянием. Пока клиент ждёт принятия выбора, показывать состояние ожидания; нельзя сразу рисовать новые иконки поверх ещё действующей старой схемы. Для предварительного выбора допускается отдельно обозначенный предпросмотр. Поворот на 90°/180°/270° поворачивает реальные позиции и направления, но названия остаются читаемыми, а порядок I1/I2/O1… относится к исходным бакам, не сортируется заново по экранному x.
- Чертёж, копирование/вставка настроек, призрак с рецептом и стройка роботом показывают тот же план портов; призрак без рецепта — нейтральную схему. У неразведанного объекта на карте не появляется лишняя информация через эту визуализацию. На близком масштабе читаются все метки; на дальнем допускается упрощение, а выбранный объект/подсказка остаётся доступным. Поддерживаются Canvas/WebGL/предусмотренный резервный рендерер и разные размеры окна.
- В окне здания добавить мини-схему с тем же поворотом и списком «Входы / Выходы»: значок, имя, место на схеме, количество на цикл. Выделение строки подсвечивает соответствующий внешний штуцер. Число строк определяется жидкостными назначениями текущего рецепта, а не всеми ингредиентами. Иконка, стрелка и текст позволяют разобраться без различения цветов.

**Единое назначение и границы изменения**

Для симуляции, подсказок, схемы окна и предпросмотра использовать общий расчёт назначения: прототип/его баки + рецепт/порядок жидких ингредиентов + `io` + преобразование положения/поворота из `fluidConns`. Фактический `ffilter` авторитетного объекта проверяется против результата, а не заменяется клиентом. Если один бак имеет несколько физических соединений, все соединения показывают одно назначение бака. Совместимые модовые рецепты обрабатываются по данным; превышение числа входных/выходных баков — диагностируемая ошибка совместимости, без придуманных дополнительных выходов на картинке.

Кэш меток учитывает прототип, рецепт, поворот и обновление клиентского состояния; переход simple → advanced → acid на подходящих зданиях не оставляет старый набор. Это визуальное исправление: оно не меняет объёмы баков, рецепты, порядок жидкостей и правила смешивания/подключения. В 1.15 смена рецепта уже вызывает `setFluidFilters`/`_clearFluid` и перестройку сети; этот путь должен исполняться только авторитетом по прежним правилам. Отрисовка/наведение/переключение Alt не очищают жидкость и не запускают повторно смену фильтров. Сообщение о неправильной жидкости показывает требуемую жидкость отдельно от фактической, без автоматической UI-очистки трубы. Для новых совместимых машин/рецептов 1.16 используется тот же контракт после их интеграции, а точная схема берётся из их прототипов, не из схемы НПЗ.

Состояние меток выводится из уже сохраняемых рецепта/поворота/данных прототипа; отдельный сохраняемый список иконок или игровая команда «обновить порты» не нужны. Локальное зеркало/Worker/поздний клиент получают достаточные данные для одинаковой схемы; визуальные предпочтения игрока не включаются в хеш мира. Подключение трубы по указанному месту должно приводить к тому же реальному баку, который показан на схеме.

**Приёмка отображения портов**

1. Все шесть примеров таблицы проверены на реальной сборке: соответствуют I/O, жидкость, количество за цикл и расположение. Отдельно проверен переход простая → глубокая переработка с переносом газового назначения O1 → O3; для пластика/серы нет ложного жидкостного выхода.
2. Каждый пример проверен при четырёх поворотах: метки/стрелки/мини-схема совпадают с действительным подключением трубы. Подача указанной жидкости и отвод через показанные выходы обеспечивают работу рецепта при прочих необходимых условиях; неверная жидкость показывает понятную причину и не переименовывает назначение порта.
3. Наведение/выделение/Alt, размещение трубы, соединённые трубы, масштабы и все поддерживаемые рендереры дают читаемый результат. Невыбранный рецепт и неиспользуемый штуцер отличаются от действующего назначения; окно доступно на небольшом экране и без различения цветов.
4. Смена рецепта/поворота, отказ сервером, чертёж/копирование/призрак/стройка роботом и совместимый модовый рецепт не оставляют устаревшие метки. Несовместимый рецепт выдаёт диагностику. UI не меняет жидкость, объёмы, ресурсы и фильтры побочным действием.
5. Одиночка/Worker/кооператив/сервер, save/load, поздний вход и перезапуск восстанавливают одну и ту же схему из игрового состояния. Проверены реальные потоки и визуальные снимки всех направлений; совпадение текста ТЗ с исходниками само по себе не означает, что проблема уже исправлена.
